# Push — FCM 푸시 알림 기획 (뼈대)

Prism의 세 번째 수직 슬라이스 **후보**. 인증이 "로그인 → 세션 → 배포"를, WebRTC가
"실시간"을 보여준다면, 이 슬라이스는 **세션 목록을 주소록으로 쓰는 첫 사례**다 —
[dashboard.md](./dashboard.md)가 만든 활성 세션 목록에서 대상을 골라 그 기기로 푸시를 보낸다.

개인정보 미저장 원칙([auth.md](./auth.md))은 여기서도 유지된다: **등록 토큰은 세션 안에서만
살고 세션과 함께 사라진다.** 별도 테이블도, 정리 잡도 두지 않는다.

> **상태: 뼈대.** §5의 결정만 확정이고 화면·계약·구현은 아직이다. 착수는
> [webrtc.md](./webrtc.md) 슬라이스 다음을 본다.

## 2. 범위

### 넣는 것 (v1)

- 내 기기 목록에서 대상을 골라 **푸시를 보내 보는 화면**
- 서버가 FCM으로 전송 — 자격증명(서비스 계정)은 env로만 주입, 레포에 두지 않는다
- 목록에 **푸시 가능 여부** 표시

### 의도적 제외

- **잠든 기기 깨우기** — 세션이 살아 있는 동안만 대상이다(§5-4)
- 토픽·세그먼트·예약 발송·알림 이력·읽음 확인
- 알림 클릭 시 딥링크 (WebRTC 착신 알림으로 이어지면 그때 다시 본다)

---

## 3. 사용자 흐름 (초안)

1. 로그인 → 푸시 화면에서 **내 기기 목록**을 본다(활성 세션 = 대시보드와 같은 목록)
2. 대상을 고르고 문구를 적어 보낸다
3. 받은 기기에 알림이 뜬다 — 리뷰어는 **기기 두 대 또는 브라우저 두 개**로 혼자 시연할 수 있다

## 4. 화면 (Figma — 착수 전)

- ⏳ 대상 목록(기기 종류 · 푸시 가능 여부) · 문구 입력 · 전송 결과
- 기기 행은 대시보드의 세션 행과 **같은 부품**을 쓴다(`Atom/Badge` · 기기 아이콘) —

## 5. 결정 (확정)

### 1. 토큰은 **세션 레코드**에 담는다

별도 테이블에 두면 기기 식별자가 Postgres와 백업에 남고, 로그아웃한 기기의 토큰을 지우는
책임이 따로 생긴다. 세션에 담으면 **로그아웃·폐기·유휴 만료가 그대로 토큰의 수명**이 된다.

- 정확히 말하면 "저장하지 않는다"가 아니라 **"세션과 함께 사라진다"**이다(Redis도 저장소다).
  얻는 것은 Postgres·백업에 남지 않고, 로그아웃하면 즉시 없어진다는 성질이다.
- **회전이 토큰을 떨어뜨리지 않는다.** `rotate()`는 자격증명만 교체하고 세션 본체는
  `renewKeys`로 TTL만 연장한다(`sessions.repository.ts`) — 레코드에 필드를 더해도 옮겨
  담는 코드가 필요 없다.

### 2. 토큰 전달은 **로그인 시점**이다

`create()`가 레코드를 쓸 때 함께 넣는다. 살아 있는 세션 레코드를 고치는 경로를 만들지
않으려는 것이다 — 그 경로가 생기면 값만 바꾸면서 **남은 TTL을 보존**해야 하는데, 지금
`RedisClient`에는 `setEx`(수명 재지정)뿐이라 잘못 쓰면 세션 수명이 리셋된다.

- ⚠️ **권한 타이밍이 남은 문제다**(§7). 웹은 알림 권한 + 서비스 워커 뒤에야 토큰이 나오고
  앱도 보통 첫 실행 이후에 묻는다 — 로그인 순간 토큰이 없을 수 있다.

### 3. 목록에 **토큰을 싣지 않는다**

기기를 가리키는 값은 이미 `SessionListItem.id`이고, 폐기가 그 id로 라우팅한다. 클라이언트는
"이 세션에 보내줘"라고만 하고 **서버가 레코드에서 토큰을 꺼낸다.**

- 클라이언트가 토큰으로 할 수 있는 일이 없다 — FCM 전송에는 서버 자격증명이 필요하다.
- 토큰은 **설치 단위**라 세션보다 오래 산다. 응답에 실으면 devtools·HAR·스크린샷에
  복사본이 남고 그것들은 세션 만료를 따라가지 않는다. 목록에는 남의 기기 행도 있다.
- 로그인 화면이 "이 포트폴리오는 개인정보를 저장하지 않습니다"(`auth.no_personal_data`)를
  띄우는 프로젝트다. 네트워크 탭 한 번에 지속적 설치 식별자가 보이면 그 주장이 무색해진다.
- 대신 **`pushRegistered: boolean`** 만 내려준다. 보안 장치가 아니라 **UI 편의**다 —
  없으면 눌러도 아무 일 없는 대상이 섞여 사용자가 이유를 모른다.
- 개발 중 토큰을 눈으로 맞춰야 하면 **끝 6자리 마스킹**이면 충분하다(주소로는 못 쓴다).

### 4. **잠든 기기는 깨우지 않는다**

세션이 살아 있는 동안만 푸시 대상이다. 며칠 닫아 둔 앱은 유휴 만료로 세션이 없고, 따라서
토큰도 없다.

- **푸시 때문에 세션 idle 수명(`PRISM_JWT_REFRESH_TOKEN_EXPIRES_IN`)을 늘리지 않는다.**
  알림 기능이 인증 정책을 끌고 가면 안 된다.
- 포트폴리오의 목적은 "푸시가 실제로 간다"를 보이는 것이라 이 한계가 시연을 막지 않는다.

### 5. 보낼 때 **토큰 기준 중복 제거**

같은 설치가 여러 세션에 걸릴 수 있다(로그아웃 후 재로그인). 세션마다 보내면 한 기기에
알림이 두 번 뜬다.

## 6. 데이터 / API 컨트랙트 (초안)

```ts
// 세션 본체(Redis) — 로그인 시점에 함께 기록된다.
interface SessionRecord {
  // ...기존 필드
  pushToken?: string; // FCM 등록 토큰. 응답으로 나가지 않는다.
}

// 목록 응답 — 토큰이 아니라 파생 불리언만.
interface SessionListItem {
  // ...기존 필드
  pushRegistered: boolean;
}
```

- `POST /push/sessions/:id` (가칭) — 대상 세션 id + 문구. 서버가 레코드에서 토큰을 꺼내
  FCM으로 보낸다. 토큰이 없으면 그 대상은 건너뛰고 사유를 돌려준다.
- 새 필드는 **없으면 false로 접는다** — 롤링 배포 중 예전 서버 응답과 섞여도 목록 전체가
  실패하면 안 된다(`decodeSessionListItem`의 `isConnected`와 같은 규칙).

## 7. 오픈 이슈

- **권한 타이밍(§5-2)** — 두 갈래가 있다. ① 로그인 화면에서 미리 알림 권한을 받아 로그인
  시점에 토큰을 손에 쥔다(로그인 전에 권한을 묻는 흐름이 된다). ② 늦게 나온 토큰만 올리는
  "현재 세션 토큰 갱신" 경로를 두고, 그때 **남은 TTL을 보존하는 헬퍼**(`KEEPTTL`류)를 더한다.
  실제 권한 흐름을 보고 정한다.
- **웹 푸시 포함 여부** — 서비스 워커 + VAPID로 배관이 앱과 다르다. v1 범위인지 미정.
- **세션 목록의 공유 저장소** — 소비자가 대시보드·WebRTC·푸시 셋이 된다. 목록은 여전히
  `GET /auth/sessions` **한 경로**로 두고(§1 "소켓은 신호만 나른다"와 같은 이유), 클라이언트
  쪽에서 한 번 받아 여러 화면이 나눠 쓰는 저장소로 올린다 — 두 번째 소비자(WebRTC 로비)가
  붙을 때 함께 한다.
- **전송 결과를 어디까지 보여줄지** — FCM은 "기기에 도달"까지만 알려준다. 표시를 과하게
  하면 없는 사실을 지어내게 된다.
