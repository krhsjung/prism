# Push — FCM 푸시 알림 기획 (뼈대)

Prism의 세 번째 수직 슬라이스 **후보**. 인증이 "로그인 → 세션 → 배포"를, WebRTC가
"실시간"을 보여준다면, 이 슬라이스는 **세션 목록을 주소록으로 쓰는 첫 사례**다 —
[dashboard.md](./dashboard.md)가 만든 활성 세션 목록에서 대상을 골라 그 기기로 푸시를 보낸다.

개인정보 미저장 원칙([auth.md](./auth.md))은 여기서도 유지된다: **등록 토큰은 세션 안에서만
살고 세션과 함께 사라진다.** 별도 테이블도, 정리 잡도 두지 않는다.

> **상태: 4플랫폼 구현 · 미배포.** 서버(전송기 · 세션에 담기는 토큰 · `pushRegistered` ·
> 전송 경로)와 네 클라이언트(푸시 화면 · 로그인 화면의 권한 줄 · 알림 수신)가 섰고,
> **소켓 없는 기기를 통화로 깨우는 경로**도 함께 붙었다([webrtc.md](./webrtc.md) §8-9).
>
> 남은 것은 **Firebase 프로젝트와 자격증명**이다 — 서비스 계정 · `google-services.json` ·
> `GoogleService-Info.plist` · APNs 인증 키 · 웹 VAPID 키. 없으면 서버는 그대로 뜨고
> `pushRegistered`가 전부 false로 접혀 화면이 `Notifications off`를 말한다.
> 실제 알림 도착 · APNs 경로 · Doze 지연은 **실기기 없이는 확인할 수 없다**(§7).

## 1. 기능 요약 (Feature Log)

형식은 [dashboard.md §1](./dashboard.md) 규칙과 같다. 구현이 붙을 때부터 최신순으로 쌓는다.

### 등록을 로그인에서 떼어냈다 (server · web · iOS · Android)

- 요약: 등록 토큰을 **살아 있는 세션에 붙인다**(`POST /auth/push/register`). 로그인 화면은
  로그인만 하고, 푸시 화면의 `알림 켜기`가 권한과 등록을 함께 끝낸다. §5-2를 뒤집은 것이다.
- 왜: "재로그인 한 번"으로 쳤던 대가가 계속 물렸다 — 한 번 허용하면 켜기 줄이 사라져
  **토큰을 얻을 길 자체가 없어졌고**, 몇 번을 다시 로그인해도 그 세션은 꺼진 채였다.
- 데이터/API: `POST /auth/push/register` · `RedisClient.setKeepTtl`(SET … KEEPTTL XX).
  로그인 요청의 `pushToken`, `POST /auth/push/pending`과 그 쿠키, `sentToken` 대조,
  "다시 로그인하세요" 문구가 **함께 사라졌다** — 순 코드가 줄었다
- 추가: 2026-09-08

### 다중 발송 · 이미지 · 링크 · 버튼 — 구현 (server · web · iOS · Android)

- 요약: 대상을 **여럿 고를 수 있고**, 알림에 **이미지 · 누르면 여는 링크 · 버튼**을
  실을 수 있다. 답은 대상마다 따로 오고, 같은 설치가 여러 세션에 걸리면 토큰 기준으로
  합쳐 한 번만 보낸다 — §5-5가 **처음 발동하는** 자리다.
- 화면: `Push` 3프레임이 체크박스 목록 · 일괄 토글 · **제목** · 이미지(샘플+주소) ·
  링크 · 버튼으로 다시 그려졌다. `Molecule/CallTarget`에 `Selectable`·`Selected` 두 변형이 늘었다.
  데스크톱은 **두 열**이 됐다 — 작성이 왼쪽, 기기 목록이 통화 로비와 같은 오른쪽 416
  ([아래](#결정됨-데스크톱은-두-열이고-목록은-오른쪽이다))
- 데이터/API: `POST /auth/push/send`(세션 하위에서 옮겼다) · `PushSendResponse.results` ·
  `PUSH_ACTION_SETS` · 페이로드의 `link`·`actions`. 이미지는 **주소만** 오간다(§5-11)
- 관련: iOS에 **Notification Service Extension 타깃**이 늘었다 — 그것 없이는 iOS만
  이미지가 빠진 채 뜬다(§5-12). 버튼 문구는 서버가 보내지 않고 세 플랫폼이 각자 그린다
- 추가: 2026-09-08

### 통화 깨우기 — 구현 (server · web · iOS · Android)

- 요약: 소켓 없는 기기를 **알림으로 깨운다**. `CallGateway`가 소켓이 없으면 세션 레코드에서
  토큰을 꺼내 FCM으로 보내고 거는 쪽에 `notified`로 답한다. 알림을 열면 앱이 소켓을 붙이고
  `resume{callId}`로 통화가 아직 살아 있는지 묻는다 — 이 저장소에서 `resume`이 **처음
  실제로 쓰이는** 자리다.
- 화면: 로비의 줄이 `#id` ↔ `Will notify`로 갈리고, 호출 중 배지가 `Ringing` ↔ `Notified`로
  갈린다. 창이 지난 뒤 열면 `Call expired` — **푸시 경로의 정상 결말**이다(webrtc.md §8-10)
- 데이터/API: 계약에 `notified` 한 줄. **새 REST 없음.** 페이로드는 `callId` + 건 기기 종류뿐
- 관련: 알림 폭탄 방지(세션당 60초에 3회)가 함께 붙어 webrtc.md §7의 "아직 아닌 것" 하나를
  갚았다. **타이머는 FCM 왕복 앞에 건다** — 기다리면 받는 쪽의 45초가 그만큼 짧아진다
- 추가: 2026-09-05

### 푸시 슬라이스 — 구현 (server · web · iOS · Android)

- 요약: 내 기기 목록에서 대상을 골라 **알림을 보내 보는 화면**. 등록 토큰은 로그인 시점에
  세션 레코드에 담기고, 목록에는 파생 불리언 `pushRegistered`만 나간다. 전송기는
  `@app/push`에 두어 auth(화면)와 socket(통화 깨우기) 두 서비스가 함께 쓴다.
- 화면: `Push` — 기기 목록(대시보드·통화 로비와 **같은 부품**) · 문구 입력 · 결과 한 줄.
  권한과 등록은 **푸시 화면이 함께** 처리한다 — 로그인 화면은 로그인만 한다(§5-2)
- 데이터/API: `SessionInfo.pushRegistered` · `POST /auth/push/send` ·
  `POST /auth/push/register`(§5-2를 뒤집으며 로그인 경로의 토큰 전달을 대체했다)
- 관련: 자격증명 셋(`PRISM_FCM_*`)은 **함께 있거나 함께 없다**(TURN과 같은 규칙).
  없으면 푸시만 꺼진 채로 나머지가 전부 동작한다
- 추가: 2026-09-05

## 2. 범위

### 넣는 것 (v1)

- 내 기기 목록에서 대상을 골라 **푸시를 보내 보는 화면**. 대상은 **여럿 고를 수 있다** —
  같은 설치가 여러 세션에 걸리면 토큰 기준으로 합쳐 한 번만 보낸다(§5-5·§5-10)
- **알림이 실을 수 있는 것을 다 싣는다**: 이미지 · 누르면 여는 링크 · 버튼(§5-11 ~ §5-13)
- **웹도 받는다** — 서비스 워커 + VAPID(§7의 닫힌 질문). 빠지면 웹 세션이 소켓 끊긴
  순간 죽은 줄이 되어 [webrtc.md](./webrtc.md) §8-9가 웹에서만 거짓이 된다
- 서버가 FCM으로 전송 — 자격증명(서비스 계정)은 env로만 주입, 레포에 두지 않는다
- 목록에 **푸시 가능 여부** 표시(`pushRegistered`) — [webrtc.md](./webrtc.md)의 로비가
  같은 값으로 `Will notify` / `Notifications off`를 가른다
- **착신 알림 딥링크** — 알림을 열면 앱이 소켓을 붙이고 `resume{callId}`로 통화가 아직
  살아 있는지 묻는다. 페이로드에는 `callId`와 건 기기 종류만 담는다
  ([webrtc.md](./webrtc.md) §6 · §7)

### 의도적 제외

- **잠든 기기 깨우기** — 세션이 살아 있는 동안만 대상이다(§5-4)
- **VoIP 푸시**(iOS `PushKit` + `CallKit` · Android `CallStyle` + high-priority FCM) —
  기기를 네이티브로 울려 [webrtc.md](./webrtc.md)의 45초 창을 지킬 수 있지만, iOS는 PushKit
  푸시를 받으면 **반드시 CallKit에 보고해야** 하고 Android는 high-priority에 할당량이 붙는다.
  둘 다 도메인이 아니라 플랫폼 통합 덩어리라 슬라이스 취지에서 벗어난다.
  대신 WebRTC 쪽이 **푸시 경로의 정상 결말을 `Call expired` + 되걸기로** 받아들인다
  ([webrtc.md](./webrtc.md) §9-10 · §10).
- 토픽·세그먼트·예약 발송·알림 이력·읽음 확인

## 3. 사용자 흐름 (초안)

1. 로그인 → 푸시 화면에서 **내 기기 목록**을 본다(활성 세션 = 대시보드와 같은 목록)
2. 대상을 고르고 문구를 적어 보낸다
3. 받은 기기에 알림이 뜬다 — 리뷰어는 **기기 두 대 또는 브라우저 두 개**로 혼자 시연할 수 있다

### 결정됨: 데스크톱은 두 열이고 목록은 **오른쪽**이다 (2026-09-08)

카드를 560으로 묶어 뒀더니 1440에서 **오른쪽 절반이 통째로 비었다.** 대시보드 카드도
통화 카드도 전폭을 쓰는데 이 화면만 절반에서 끊긴 것이다. 폭을 좁혀 목록이 양 끝으로
갈라지는 것을 막을 일이 아니라, **목록에 제 열을 주면 되는 일**이었다.

- **목록이 오른쪽인 이유**: 통화 로비의 `.setup`이 오른쪽 `clamp(300px, 38%, 416px)`이다.
  같은 기기 행 부품이 화면을 옮길 때마다 좌우를 바꾸면, 아래의 "같은 부품이다"가 그림에서
  거짓이 된다. **폭까지 같게** 둔다 — 열의 자리가 같아야 같은 자리로 읽힌다.
- **보내기는 두 열 아래 전체 폭이다.** 작성 열(문구+이미지+샘플+링크+버튼)이 기기 4행보다
  훨씬 길어서, 버튼을 열 안에 두면 카드 바닥이 한쪽만 길어진다.
- **줄바꿈하지 않는다.** 자리가 모자랄 때 접히게 두면 1120 같은 평범한 창에서 목록이
  작성란 아래로 내려간다 — 세로로 쌓이는 것은 375의 일이다(통화 로비와 같은 규칙).
- **375에서도 `order`로 뒤집지 않는다.** 보이는 순서와 탭 순서가 갈라지면 키보드가 화면과
  다른 길을 간다. 쌓이는 순서는 데스크톱의 읽는 순서 그대로 **작성 → 목록 → 보내기**이고,
  결과 줄이 보내기 버튼 바로 위에 온다.
- **카드 껍데기도 대시보드·통화 카드와 같아졌다** — 머리 / 본문 / 바닥 세 구획에 구분선.
  바닥 한 줄은 **토큰이 어디에 사는지** 말한다(§5-3). 웹이 그 구획을 빠뜨리고 있었다.

### 결정됨: 기기 행은 통화 로비와 **같은 부품**이다

`Molecule/CallTarget`을 그대로 쓴다 — 같은 목록(`GET /auth/sessions`)을 두 화면이 다르게
그리면 그것부터 설명해야 한다. 다른 것은 **할 수 있는 일**뿐이라 오른쪽 자리만 갈린다:
로비는 `Call`, 여기는 **체크박스**(`State=Selectable` · `Selected` 두 변형을 더했다).

- **버튼이 아니라 체크박스인 이유**: 여럿 고를 수 있다는 것을 컨트롤의 모양이 먼저
  말한다. 버튼이면 하나만 고르는 것으로 읽힌다(§5-10).
- **목록 머리가 고른 수를 말하고 한 번에 바꾼다**(`2 selected` · `Select all`). 기기가
  여럿일 때 줄마다 누르는 것이 유일한 길이면 손이 많이 간다. 기기가 하나뿐이면 이
  컨트롤은 나오지 않는다 — 바꿀 것이 없는 자리에 컨트롤을 두지 않는다.

- **행의 상태를 가르는 기준도 다르다.** 로비는 "닿는가"(소켓 또는 토큰), 푸시 화면은
  "등록됐는가"(토큰)다. 그래서 소켓만 없는 기기가 로비에서는 `Will notify`인데 여기서는
  평범한 대상이다.
- **현재 세션도 대상이다.** 로비에서 그 줄은 루프백 시험이지만(webrtc.md §4) 여기서는
  고를 수 있는 줄이다 — 기기를 하나만 가진 리뷰어가 **자기 자신에게 보내** 알림이 실제로
  뜨는 것을 확인할 수 있어야 한다. 통화의 루프백과 같은 자리다.
- **결과도 그 줄에 그린다.** 보낸 뒤에는 부제가 `#세션id`에서 그 줄의 결말로 바뀐다 —
  목록 밖에 결과를 모아 두면 어느 기기가 어떻게 됐는지를 다시 짝지어 읽어야 한다(§5-10).

### 결정됨: 알림이 실을 수 있는 것은 **셋 다 선택**이다

제목 · 문구가 위에 서고 그 아래로 이미지 · 링크 · 버튼이 차례로 선다. 비워 두면
문구만 있는 알림이 된다.

- **제목이 문구보다 위다** — 알림에서 읽히는 순서가 그렇다. 비워 두면 서버가 받는
  기기의 언어로 그리므로 필수 표시를 두지 않는다(§5-14).

- **이미지 샘플은 색 자체가 미리보기라 이름표가 없다.** `이미지 없음`만 글자를 갖는다 —
  색으로 표현할 수 없는 유일한 선택지이기 때문이다.
- **버튼은 세 조합이 나란히 선다.** 드롭다운이 아니라 눈에 보이는 선택지인 이유는 셋뿐이고,
  고른 것이 화면에 남아 있어야 "이 알림에 버튼이 붙는다"가 보이기 때문이다.
  375에서는 한 줄에 들어가지 않아 접힌다.

### 결정됨: 사이드바가 세 번째 항목을 얻었다 (자리는 2026-09-08 갱신)

`Organism/Sidebar`에 `Push`가 붙어 **모든 화면의 사이드바가 함께 바뀐다.** 앱이 세
페이지인데 시안이 둘만 그리면, 시안을 보는 사람이 없는 앱을 상상하게 된다.

**자리는 대시보드와 통화 사이다.** 붙인 순서대로 맨 뒤에 뒀다가 옮겼다 — 알림을 한 번
보내 보는 것이 통화를 걸어 보는 것보다 **앞선 단계**이고, 통화 깨우기가 푸시 위에 서
있으므로(§5-4 · webrtc.md §8-9) 읽는 차례도 그쪽이다. 네 플랫폼이 같은 차례를 쓴다 —
웹 `NAV` · iOS `ShellPage` · Android `ShellPage`, 그리고 시안의 `Organism/Sidebar`.

## 5. 결정 (확정)

### 1. 토큰은 **세션 레코드**에 담는다

별도 테이블에 두면 기기 식별자가 Postgres와 백업에 남고, 로그아웃한 기기의 토큰을 지우는
책임이 따로 생긴다. 세션에 담으면 **로그아웃·폐기·유휴 만료가 그대로 토큰의 수명**이 된다.

- 정확히 말하면 "저장하지 않는다"가 아니라 **"세션과 함께 사라진다"**이다(Redis도 저장소다).
  얻는 것은 Postgres·백업에 남지 않고, 로그아웃하면 즉시 없어진다는 성질이다.
- **회전이 토큰을 떨어뜨리지 않는다.** `rotate()`는 자격증명만 교체하고 세션 본체는
  `renewKeys`로 TTL만 연장한다(`sessions.repository.ts`) — 레코드에 필드를 더해도 옮겨
  담는 코드가 필요 없다.

### 2. 등록은 **푸시 화면에서** 한다 (2026-09-05 결정 → 2026-09-08 뒤집음)

**처음 결정은 "로그인 시점에만"이었다.** `create()`가 레코드를 쓸 때 토큰을 함께 넣고,
살아 있는 세션을 고치는 경로는 만들지 않는다 — 그 경로가 생기면 값만 바꾸면서 남은 TTL을
보존해야 하는데 당시 `RedisClient`에는 `setEx`(수명 재지정)뿐이라 잘못 쓰면 세션 수명이
리셋되기 때문이었다. 대가는 "재로그인 한 번"으로 쳤다.

**그 계산이 틀렸다.** 배포하고 써 보니 대가가 한 번이 아니라 계속 물렸다:

- 권한은 로그인 **전에** 받아야 해서, 로그인 화면이 알림 이야기를 해야 했다
- 한 번 허용하고 나면 `알림 켜기` 줄이 사라져 **토큰을 얻을 길 자체가 없어졌다** —
  몇 번을 다시 로그인해도 그 세션은 `Notifications off`였다(실제로 그랬다)
- 화면은 "다시 로그인하세요"를 계속 설명해야 했고, 그 안내가 안 뜨는 갈래도 있었다
- 웹 소셜 로그인은 body가 없어 토큰을 **쿠키로 날라야** 했다(경로 하나 + 쿠키 하나)

그 사이 `SET ... KEEPTTL`이 들어와(`compareAndRenew`가 쓴다) **기술적 이유도 사라졌다.**

→ **`POST /auth/push/register`로 살아 있는 세션에 붙인다.** 푸시 화면의 `알림 켜기`가
권한과 등록을 함께 끝내고, **로그인 화면은 로그인만 한다.**

- **유휴 창을 밀지 않는다.** `setKeepTtl`(SET … KEEPTTL XX)로 값만 간다. 알림을 켜는 것은
  사용자의 손짓이지만 그것으로 수명을 밀면 유휴 창이 "손을 뗀 지 얼마나 됐나"를 말하지
  않게 된다(auth.md §6). `XX`라서 그 사이 만료된 세션을 되살리지도 않는다.
- **소유권은 저장소가 확인한다** — 남의 세션 id로 남의 기기에 토큰을 심을 수 있으면 그것
  자체가 공격이다(`pushTargetFor`와 같은 자리).
- **함께 사라진 것들**: 로그인 요청의 `pushToken`, 웹 소셜용 `POST /auth/push/pending`과
  그 쿠키, 회전을 알아채려 저장하던 `sentToken`, 그리고 "다시 로그인하세요" 문구.
  **순 코드가 줄었다.**
- **남은 대가 하나**: FCM이 토큰을 회전시켜도 세션은 옛 토큰을 들고 있다. 다만 이제
  푸시 화면에서 `알림 켜기`를 한 번 누르면 붙으므로, 재로그인까지 갈 일은 없다.

### 3. 목록에 **토큰을 싣지 않는다**

기기를 가리키는 값은 이미 `SessionListItem.id`이고, 폐기가 그 id로 라우팅한다. 클라이언트는
"이 세션에 보내줘"라고만 하고 **서버가 레코드에서 토큰을 꺼낸다.**

- 클라이언트가 토큰으로 할 수 있는 일이 없다 — FCM 전송에는 서버 자격증명이 필요하다.
- 토큰은 **설치 단위**라 세션보다 오래 산다. 응답에 실으면 devtools·HAR·스크린샷에
  복사본이 남고 그것들은 세션 만료를 따라가지 않는다. 목록에는 남의 기기 행도 있다.
- 로그인 화면이 "이 포트폴리오는 개인정보를 저장하지 않습니다"(`auth.no_personal_data`)를
  띄우는 프로젝트다. 네트워크 탭 한 번에 지속적 설치 식별자가 보이면 그 주장이 무색해진다.
- 대신 **`pushRegistered: boolean`** 만 내려준다. 보안 장치가 아니라 **UI 편의**다 —
  없으면 눌러도 아무 일 없는 대상이 섞여 사용자가 이유를 모른다.
- 개발 중 토큰을 눈으로 맞춰야 하면 **끝 6자리 마스킹**이면 충분하다(주소로는 못 쓴다).

### 4. **잠든 기기는 깨우지 않는다**

세션이 살아 있는 동안만 푸시 대상이다. 며칠 닫아 둔 앱은 유휴 만료로 세션이 없고, 따라서
토큰도 없다.

- **푸시 때문에 세션 idle 수명(`PRISM_JWT_REFRESH_TOKEN_EXPIRES_IN`)을 늘리지 않는다.**
  알림 기능이 인증 정책을 끌고 가면 안 된다.
- 포트폴리오의 목적은 "푸시가 실제로 간다"를 보이는 것이라 이 한계가 시연을 막지 않는다.

### 5. 보낼 때 **토큰 기준 중복 제거**

같은 설치가 여러 세션에 걸릴 수 있다(로그아웃 후 재로그인). 세션마다 보내면 한 기기에
알림이 두 번 뜬다.

- **이번 구현에서는 발동하지 않는다** — 전송도 통화 깨우기도 대상이 한 세션뿐이라 중복이
  생길 자리가 없다. 다중 발송(전체 기기에 보내기 같은 것)이 생기면 그때 전송기 안에
  붙인다. 규칙을 지금 세워 두는 이유는 그때 이 결정을 다시 하지 않기 위해서다.

### 6. ~~웹 소셜 로그인은 쿠키로 토큰을 나른다~~ — 폐기 (2026-09-05 → 2026-09-08)

웹 소셜 로그인은 세션이 **서버 콜백**에서 만들어져 토큰을 실을 body가 없다. 그래서
떠나기 직전 짧은 수명의 HttpOnly 쿠키에 맡기고 콜백이 읽어 넘겼다 —
`POST /auth/push/pending` 하나와 쿠키 하나가 그것 때문에 있었다.

**§5-2를 뒤집으면서 통째로 사라졌다.** 로그인이 토큰을 나르지 않으니 실을 자리를 찾을
일도 없다. 경로·쿠키·헬퍼(`push-cookie.ts`)와, 그 쿠키를 심는 문을 지키던
`WebOriginGuard` 한 겹까지 함께 걷어냈다.

**남는 교훈 하나** — 흐름의 제약(토큰이 로그인에 실려야 한다)을 우회하려고 만든 배관은,
그 제약이 사라지면 함께 사라져야 한다. 남겨 두면 아무도 부르지 않는 인증 경로가 된다.

### 7. 알림 문구는 **서버가 세션의 언어로** 그린다 (2026-09-05)

받는 기기의 언어는 **보내는 요청에서 알 수 없다.** 세 갈래를 봤다:

- `title_loc_key`/`body_loc_key` → iOS가 모듈별 `.xcstrings`를 쓰므로 `Localizable`을 보는
  loc-key가 **해석되지 않는다**(키 문자열이 그대로 뜬다). 웹에는 문자열 표 자체가 없다.
- data-only + 클라이언트 렌더 → **iOS 무음 푸시는 알림을 띄우지 못한다**(저전력 모드·강제
  종료에서 조용히 사라진다). 푸시가 존재하는 이유인 바로 그 경우에 실패한다.
- **세션에 언어를 함께 담고 서버가 그린다** ← 이것. `translate(locale, key)`가 이미 있고,
  OAuth 콜백 페이지가 이미 이 방식으로 서버가 직접 그리는 문구를 다룬다.

**언어는 계약이 아니라 `Accept-Language`가 나른다.** 네 클라이언트가 헤더를 붙이기
시작했고(앱 안에서 고른 언어 — 기기 설정이 아니다), 서버는 `deviceOf` 옆의 `localeOf`로
접어 세션에 담는다. 계약에 필드를 더하는 것보다 나은 이유: 이미 있는 헬퍼를 쓰고,
**웹 OAuth 리다이렉트 경로가 공짜로 해결되며**(브라우저가 알아서 싣는다), 문서화돼 있던
"클라이언트가 Accept-Language를 안 보낸다"는 구멍이 함께 닫힌다.

**기기 종류는 알림 본문에 넣지 않는다.** 넣으면 기기 라벨 9개를 서버 문구 마스터에
복제해야 하고, 그 사본은 `client.csv`와 갈라진다. 종류는 `data`로 가고 **앱을 연 화면이**
그린다 — `expired` 화면이 `from`을 그렇게 쓰는 것과 같은 자리다(webrtc.md §6).

### 8. 전송은 이미 있는 `google-auth-library`로 한다 (2026-09-05)

`firebase-admin`은 gRPC·Firestore·Storage까지 끌고 온다 — 엔드포인트 하나 때문에 이미지
셋에 그 스택을 넣을 이유가 없다.

그렇다고 전부 손으로 쓰지도 않는다. Apple client secret이 싼 이유는 그것이 *자기 완결적인
assertion*이기 때문이다(한 번 서명해 건네면 끝). FCM은 거기에 **토큰 교환 + 만료·갱신
캐시**가 붙는데, 그게 조용히 어긋나는 자리다(시계 오차 · 만료 순간의 동시 갱신 · 401 재시도).

→ `google-auth-library`는 `GoogleOAuthClient`가 **이미 쓰고 있다.** 그 `JWT` 클라이언트가
서명·교환·캐시를 하고 전송은 `fetch` POST 하나다. **신규 의존성 0.** 우리가 소유하는 것은
페이로드뿐이고, 그건 순수 함수로 남아 "무엇이 알림에 실리는가"를 스펙 하나가 못박는다.

### 9. 전송 경로는 `POST /auth/push/send`다 (2026-09-05, 2026-09-08 갱신)

§6의 가칭은 `POST /push/sessions/:id`였다. nginx가 `/auth`·`/api`·`/socket`만 프록시하고
나머지는 웹 정적으로 보내므로([infra/deploy/README.md](../infra/deploy/README.md)),
최상위 `/push`를 열면 **nginx 설정이 하나 늘고** 웹 SPA의 `/push` 페이지와 접두어가 겹친다.
그래서 `/auth` 아래에 둔다.

**세션 하위(`sessions/:id/push`)에서 옮겼다**(2026-09-08). 대상이 여럿이라 `:id` 하나에
담기지 않는다. 단일 발송은 **대상이 하나인 다중 발송**이므로 경로를 둘로 두지 않는다 —
두면 규칙이 둘이 되고, 언젠가 한쪽만 고쳐진다.

### 10. 다중 발송 — 답은 **대상마다** 따로 준다 (2026-09-08)

한 요청으로 여러 기기에 보낸다. 그러면서 세 가지가 따라온다.

- **결과가 배열이 된다.** `{ result }` 하나로는 "셋 중 둘은 갔고 하나는 토큰이 없다"를
  말할 수 없다. 화면은 고른 줄 **옆에** 그 줄의 결말을 그린다.
- **한 대상이 실패해도 나머지는 간다.** 요청 전체를 접으면 "하나가 방금 로그아웃해서
  아무에게도 안 갔다"가 된다. 그래서 남의 세션·없는 세션은 404가 아니라 그 줄의
  결과(`unknown`)다 — **둘을 구별해 주지 않는 규칙은 그대로다**(§6의 `unknown-session`과
  같은 이유). 목록에서 고른 id라 새로 새는 정보도 없다.
- **§5-5가 여기서 처음 발동한다.** 같은 설치가 여러 세션에 걸리면(로그아웃 후 재로그인)
  세션마다 보낼 때 한 기기에 알림이 두 번 뜬다. 토큰 기준으로 합쳐 한 번만 보내고,
  합쳐진 줄은 `duplicate`로 답한다 — **실패가 아니라 "한 번만 보냈다"는 사실**이라
  화면이 "셋을 골랐는데 알림이 둘"을 설명할 수 있다.

중복 제거가 **서비스에 사는 이유**: 세션 → 토큰 지도를 아는 곳이 거기뿐이고, 화면에
돌려줄 답도 세션 단위다. 전송기는 토큰 하나만 안다.

### 11. 이미지는 **주소로만** 온다 (2026-09-08)

이 프로젝트에는 파일 저장소가 없다. 업로드를 받으면 저장소가 생기고, 그 저장소는
"개인정보를 저장하지 않습니다"와 부딪히며 정리 잡·용량 상한이 따라온다.

→ 알림에 싣는 것은 **공개 https 주소**다. 웹 앱이 서빙하는 샘플 몇 장을 눌러 바로
시연할 수 있고, 직접 주소를 넣어도 된다.

- **서버는 그 주소를 가져오지 않는다.** 이미지는 FCM이 내려받아 붙이고 링크는 기기가
  연다 — 그래서 서버 쪽에 SSRF 표면이 생기지 않는다. 여기서 보는 것은 형식뿐이다.
- **https만 받는다.** 서버가 열지 않으니 SSRF는 아니지만, `javascript:` 같은 스킴이
  기기에서 열리는 길을 열지 않는다 — 알림을 여는 것은 사람이고, 사람은 주소를 보지 않는다.
- **로컬 개발에서는 샘플이 보이지 않는다.** FCM이 `localhost`를 가져올 수 없기 때문이다.
  배포된 주소에서만 이미지가 뜬다 — 정직하게 적어 둔다.
- **그리는 것은 결국 OS다**(2026-09-08 시연에서 확인). 주소가 맞고 페이로드가 맞아도
  플랫폼이 그릴 자리를 갖고 있지 않으면 그림은 그냥 빠진다:

  | 받는 곳 | 이미지 |
  | --- | --- |
  | Android(앱·Chrome) · Windows/Linux Chrome | 뜬다 |
  | iOS(앱) | 뜬다 — 단 Notification Service Extension이 있어야 한다(§5-12) |
  | **macOS Chrome** | **안 뜬다** — Chrome 59부터 macOS 알림 센터를 쓰는데 큰 그림 자리가 없다 |
  | macOS Safari | 안 뜬다 |

  **이것은 고칠 수 있는 것이 아니다.** `showNotification`의 `image`가 조용히 무시되는
  것이라 우리 쪽에는 실패도 남지 않는다. 시연은 Android에서 하고, 데스크톱에서 그림이
  없다고 배관이 깨진 것으로 읽지 않는다.

### 12. iOS 이미지는 **앱 확장 하나**를 요구한다 (2026-09-08)

FCM에 이미지를 실어도 iOS는 그냥 무시한다. 알림을 그리기 전에
`Notification Service Extension`이 불려 이미지를 내려받아 붙여야 하고, 그 확장이
불리는 조건이 `aps.mutable-content: 1`이다.

→ **확장 타깃을 둔다.** 안 두면 같은 기능이 iOS에서만 다르게 동작하는데, 이 저장소가
증명하려는 것이 "같은 앱이 네 플랫폼에서 같게 동작한다"이므로 그쪽이 더 비싸다.
확장은 하는 일이 한 가지뿐이다 — FCM 헬퍼에 알림을 넘기고 받아 적는다.

### 13. 버튼은 **조합을 계약이 정하고 문구는 클라이언트가 그린다** (2026-09-08)

iOS는 `UNNotificationCategory`를 **앱 시작 시 미리 등록**해야 하고 등록된 조합만 쓸 수
있다 — 서버가 그때그때 만든 버튼 목록을 보낼 방법이 애초에 없다. 그래서 조합 자체를
계약이 정한다(`none` · `open` · `open-dismiss`).

**문구는 서버가 보내지 않는다.** iOS는 등록 시점에 문구가 굳는데 그때는 요청이 없어
받는 사람의 언어를 알 수 없다. 세 플랫폼이 각자 자기 i18n으로 그린다 — 기기 라벨을
`server.csv`에 복제하지 않은 것과 **같은 이유**다(§5-7).

- Android는 `NotificationCompat.Action`, iOS는 등록된 카테고리, 웹은 Notification API의
  `actions`. 셋이 같은 값을 받아 각자의 방식으로 그린다.
- 웹은 버튼이 있으면 알림이 스스로 사라지지 않게 한다(`requireInteraction`) — 누를 것이
  있는데 지나가 버리면 버튼을 둔 의미가 없다.

### 14. 제목은 **적으면 그대로, 비우면 서버가 그린다** (2026-09-08)

D4는 알림 문구를 **서버가 세션의 언어로** 그리기로 했다. 받는 기기의 언어를 보내는
요청에서 알 수 없기 때문이다. 그래서 처음에는 제목이 `push.demo_title` 하나로 고정이었고,
화면에는 문구 입력 하나뿐이었다.

**시연에서 그 고정이 답답했다** — "테스트 푸시"밖에 못 보내니 무엇을 보내 보는 알림인지
구별되지 않았다. 그래서 제목을 선택 입력으로 열되, **번역과 맞바꾼다**:

- **적어 보내면 그 글자가 그대로 간다.** 사람이 적은 제목을 번역할 수는 없고, **본문이
  이미 같은 성질이다** — 제목만 번역을 고집할 이유가 없다.
- **비우면 서버가 받는 기기의 언어로 그린다**(`push.demo_title`). 빈 문자열과 미지정을
  가르지 않는다 — 둘 다 "안 적었다"이고 화면에서도 같은 상태다.
- **통화 알림은 이 경로를 지나지 않는다.** `CallGateway`가 직접 보내므로 제목은 여전히
  서버가 `push.call_title`로 그린다. 걸려 온 통화는 사람이 문구를 적는 자리가 아니다.
- 상한은 60자다(본문 120의 절반) — 잠금화면이 제목을 한 줄로 자른다.

### 15. 끌 수 있는 것은 **등록뿐이다** (2026-09-10)

푸시 화면에 `알림 켜기`가 생기자 곧바로 "그럼 끄기는?"이 나왔다. 그런데 **브라우저·OS의
알림 권한은 한 방향으로만 움직인다** — `Notification.requestPermission()`은 `default`에서만
뜻이 있고, 되돌리는 API는 없다(iOS·Android도 같다. 설정 앱에서만 끈다).

그래서 토글이 **약속할 수 있는 것만** 약속하게 했다:

- **끄기 = 이 세션을 푸시 대상에서 뺀다**(`POST /auth/push/unregister`). 레코드에서
  `pushToken`을 지운다. 그것이 목록의 `Notifications off`가 **이미 말하던 값**이라,
  토글과 줄이 같은 사실을 가리킨다.
- **권한은 건드리지 않는다.** 설명 줄이 그렇게 말한다 —
  *"이 기기가 더 이상 받지 않습니다. 브라우저 권한은 그대로입니다."*
- **기기의 등록 토큰은 남겨 둔다.** 다시 켤 때 권한 창이 뜨지 않는다 — 껐다 켜는 것이
  가벼운 동작이어야 토글이라 부를 수 있다.
- 유휴 창은 밀지 않는다(`setKeepTtl`). 켜기와 같은 규칙이다(§5-2).

**하지 않은 것**: "권한이 꺼진 것처럼 보이게" 하는 것. 권한이 남아 있는데 화면이 껐다고
말하면, 나중에 설정에서 권한을 확인한 사람에게 화면이 거짓말한 것이 된다.

### 16. 선택은 **기기에 남는다** (2026-09-10)

등록은 세션에 붙는다(§5-2). 그래서 로그아웃하면 함께 사라지고, 다시 로그인하면 그 세션은
대상이 아니다 — 사람이 매번 `알림 켜기`를 눌러야 했다. **그러면 토글이 "켜 두는 것"이
아니라 "매번 켜는 것"이 된다.**

→ **선택만 기기에 남기고**(`localStorage`의 `prism.push.enabled`), 로그인한 뒤 그 선택대로
조용히 다시 붙인다. 사람이 한 번 켜 두면 계속 켜져 있다.

- **토큰은 남기지 않는다.** 토큰은 회전하므로 저장하면 금세 거짓이 된다 — 필요할 때 FCM에서
  지금 값을 받으면 되고, 그래야 저장소에 남는 것이 "선택" 하나로 줄어든다.
- **권한 창은 뜨지 않는다.** 이미 `granted`일 때만 부르고, 그 상태의
  `requestPermission()`은 묻지 않고 곧바로 돌아온다 — "진입만으로 묻지 않는다"
  (webrtc.md §7)는 규칙은 그대로다. 권한이 없으면 아무것도 하지 않는다.
- **회전된 토큰이 여기서 함께 낫는다.** 로그인마다 지금 토큰을 받아 붙이므로, §7이 열어
  두었던 "회전하면 스스로 낫지 않는다"가 닫힌다. 남는 구멍은 **한 세션을 오래 열어 둔 채
  토큰이 회전하는 경우**뿐이고, 그때는 푸시 화면에서 한 번 껐다 켜면 된다.
- 붙이는 자리는 `AuthProvider`다 — 화면이 아니라 **인증 상태**에 달린 일이라, 어느 화면으로
  들어와도 한 번만 돈다.

## 6. 데이터 / API 컨트랙트

```ts
// 세션 본체(Redis) — 로그인 시점에 함께 기록된다. **둘 다 응답으로 나가지 않는다.**
interface SessionRecord {
  // ...기존 필드
  pushToken?: string; // FCM 등록 토큰
  locale?: Locale;    // 알림 문구를 그릴 언어(§5-7)
}

// 목록 응답 — 토큰이 아니라 파생 불리언만(§5-3).
interface SessionInfo {
  // ...기존 필드
  pushRegistered: boolean;
}

// 보내는 요청. **토큰은 없다** — 대상은 세션 id로 가리키고 서버가 꺼낸다.
interface PushSendRequest {
  sessionIds: string[];
  message: string;
  title?: string;      // 비우면 서버가 세션의 언어로 그린다(§5-14)
  imageUrl?: string;   // 공개 https. 서버는 가져오지 않는다(§5-11)
  link?: string;       // 누르면 여는 곳
  actions?: PushActionSet;
}

// 답은 **대상마다** 따로 온다(§5-10).
const PUSH_SEND_RESULTS = [
  'accepted',   // FCM이 접수했다
  'no-token',   // 내 세션이지만 등록 토큰이 없다
  'rejected',   // FCM이 그 토큰을 거부했다(회전된 토큰)
  'duplicate',  // 같은 설치의 다른 세션이 이미 받았다 — 실패가 아니다
  'unknown',    // 내 것이 아니거나 없는 세션. **둘을 구별해 주지 않는다**
] as const;
interface PushSendResponse {
  results: { sessionId: string; result: PushSendResult }[];
}

// 버튼 조합. iOS가 미리 등록한 것만 쓸 수 있어 **조합 자체를 계약이 정한다**(§5-13).
const PUSH_ACTION_SETS = ['none', 'open', 'open-dismiss'] as const;

// 알림 페이로드의 data 키. 세 클라이언트가 같은 문자열을 손으로 베끼지 않게.
const PUSH_DATA_KEYS = {
  KIND: 'kind',
  CALL_ID: 'callId',
  DEVICE: 'device',
  LINK: 'link',
  ACTIONS: 'actions',
} as const;
const PUSH_KINDS = ['call', 'demo'] as const;

const MAX_PUSH_TOKEN_LENGTH = 4096;
const MAX_PUSH_MESSAGE_LENGTH = 120;
const MAX_PUSH_TARGETS = 20;
const MAX_PUSH_URL_LENGTH = 2048;
```

- **`POST /auth/push/send`** — 대상 세션 id들 + 내용. 서버가 레코드에서 토큰을 꺼내
  보내고 **대상마다 결말을 답한다**(§5-10). 문구가 비었거나 상한을 넘거나 주소가
  https가 아니면 400, FCM이 지금 안 되면 502 — 그건 계약의 결과가 아니라 오류다.
- **`POST /auth/push/register`** — 지금 세션에 등록 토큰을 붙인다(§5-2). 형식이 아니면
  400. 그 세션이 사라졌으면 `{ registered: false }` — 화면은 목록을 다시 불러 사실을
  말한다. **유휴 창을 밀지 않는다**(SET … KEEPTTL XX).
- **로그인 요청은 토큰을 나르지 않는다** — 네 플랫폼 모두 로그인 화면에서 푸시를 걷어냈다.
- 새 필드는 **없으면 false로 접는다** — 롤링 배포 중 예전 서버 응답과 섞여도 목록 전체가
  실패하면 안 된다(`decodeSessionListItem`의 `isConnected`와 같은 규칙).
- **네이티브 계약은 생성되지 않는 부분이 있다.** 생성기는 문자열 배열·레코드만 옮기므로
  `PUSH_SEND_RESULTS`·`PUSH_KINDS`·`PUSH_ACTION_SETS`·`PUSH_DATA_KEYS`는 생성되고,
  숫자 상수와 `SessionListItem`의 필드는 iOS `AuthContracts.swift`·Android `Decode.kt`에
  손으로 넣는다.

## 7. 오픈 이슈

- ~~회전된 토큰은 스스로 낫지 않는다~~ — **거의 닫혔다**(§5-16). 로그인할 때마다 지금
  토큰을 받아 다시 붙이므로 회전은 다음 로그인에 낫는다. 남는 것은 **한 세션을 오래 열어
  둔 채 회전하는 경우**뿐이고, 그때는 푸시 화면에서 껐다 켜면 된다. 회전을 실시간으로
  알아채는 경로(FCM의 `onTokenRefresh` 계열)는 두지 않았다 — 세 플랫폼에 각각 붙여야
  하는데, 남은 구멍의 크기가 그 값을 넘지 않는다.
- **전송 결과를 어디까지 보여줄지** — FCM은 "받아들였다"까지만 알려준다. 지금 화면은
  딱 그만큼만 말한다(`Sent. It shows on that device if the device is awake.`).
  배달·열람을 말하려면 없는 사실을 지어내게 된다.
- **알림 폭탄 상한은 세션당이다**(60초에 3회, [webrtc.md](./webrtc.md) §7). 프로세스
  메모리라 파드가 여럿이 되면 그 수만큼 곱해진다 — `ConnectionRegistry`·통화 상태와
  **같은 자리에서 같은 승격**(Redis)을 한다.
