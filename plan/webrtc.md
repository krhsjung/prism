# WebRTC — 1:1 화상 통화 기획

Prism의 두 번째 수직 슬라이스. 인증 슬라이스가 "로그인 → 세션 → 배포"를 4플랫폼에
걸쳐 **구현 품질·일관성**으로 보여줬다면, 이 슬라이스는 거기에 **실시간(RTC)** 이라는
난이도 있는 축을 더한다 — 같은 백엔드/계약을 web·iOS·Android가 공유하는 그림은 그대로.

개인정보 미저장·원클릭 데모 원칙([auth.md](./auth.md))은 여기서도 유지된다: **미디어는
P2P로만 흐르고 서버를 거치지 않으며, 녹화·저장하지 않는다.**

**통화 상대는 내 활성 세션이다.** 방도, 코드도, 초대 링크도 없다 — 대시보드가 이미 그리는
세션 목록에서 기기를 골라 건다. 그래서 인증 슬라이스가 만들어 둔 것(세션 · presence 소켓)이
이 슬라이스의 **입력**이 된다. 리뷰어는 **탭 두 개**로 서로 걸어 보거나, 탭 하나로
**루프백 시험**을 돌려 볼 수 있다.

> **상태: 구현 완료 · 배포 전.** §8 결정을 마치고 Figma
> [`WebRTC` 페이지](https://www.figma.com/design/sTDo6HDslOcRmWL78klk1I/Prism?node-id=3036-282)에
> 11프레임을 그린 뒤(§4), 시그널링 게이트웨이와 web·iOS·Android 구현이 모두 섰다.
> **실제 통화가 오간다** — 웹↔Android · iOS↔Android(둘 다 STUN 경유) · 세 플랫폼의 루프백.
> **푸시 깨우기도 붙었다**(2026-09-05, [push.md](./push.md)) — 소켓 없는 기기는 알림으로
> 깨우고, 알림을 열면 `resume`이 통화를 이어받는다. 남은 것은 ICE restart 재연결과,
> 푸시 경로의 **실기기 검증**이다(45초 창을 실제로 지키는지는 아래 §9가 열어 둔 질문이다).

### 푸시 깨우기 — 구현 (server · web · iOS · Android)

- 요약: **소켓 없는 기기를 알림으로 깨운다**(§8-9). `CallGateway`가 소켓이 없으면 세션
  레코드에서 등록 토큰을 꺼내 FCM으로 보내고 거는 쪽에 `notified`로 답한다. 알림을 열면
  앱이 소켓을 붙이고 `resume{callId}`로 통화가 아직 살아 있는지 묻는다 — **`resume`이
  처음 실제로 쓰이는** 자리이고, 그 전까지는 서버에만 구현돼 있던 경로다.
- 화면: 로비의 줄이 `#id` ↔ `Will notify`로, 호출 중 배지가 `Ringing` ↔ `Notified`로
  갈린다. 창이 지난 뒤 열면 [`Call expired`](https://www.figma.com/design/sTDo6HDslOcRmWL78klk1I/Prism?node-id=3079-1704) — **푸시 경로의 정상 결말**(§8-10)
- 데이터/API: 계약에 `notified` 한 줄(디코더는 손대지 않았다 — `callId`만 실어 기본
  갈래가 그대로 받는다). **새 REST 없음.** 페이로드는 `callId` + 건 기기 종류뿐(§7)
- 관련: **알림 폭탄 상한**이 함께 붙었다(세션당 60초에 3회) — §7이 "아직 아닌 것"으로
  남겨 둔 항목이다. 소켓이 없을 때만 벨을 배달하는 `opened()` 훅도 더했다: 알림을 **열지
  않고** 앱만 연 경우에는 `resume`이 오지 않기 때문이다
- 추가: 2026-09-05

### 세션 소켓 수명 통일 — 배포됨

- 요약: 소켓이 **클라이언트가 살아 있는 동안** 열려 있다는 규칙을 세 플랫폼에 같게 심었다.

  재시도 폭풍만 돌리고 있었다. 웹은 숨은 탭에서도 **실제로 벨이 배달되는 것**을 실측했다.

- 관련: 백그라운드 모바일에 닿는 길은 소켓이 아니라 푸시다 — 그전까지는 목록에
  `알림 꺼짐`으로 정직하게 나온다
- 추가: 2026-09-03

## 2. 범위

### 넣는 것 (v1)

- **1:1 P2P 화상/음성 통화** — mesh/SFU 없이 두 피어가 직접 연결.
- **통화 상대는 내 활성 세션이다.** 대시보드가 이미 보여 주는 그 목록
  ([dashboard.md](./dashboard.md))에서 기기를 골라 건다. 방도, 코드도, 초대 링크도 없다.
- **루프백 자기 시험** — 목록 맨 위의 `This tab` 줄. 한 페이지 안에서 두
  `RTCPeerConnection`을 이어 **시그널링 서버를 거치지 않고** 카메라·ICE·지표가 도는 것을
  보여준다. 리뷰어가 탭 하나로도 진단 패널까지 볼 수 있다.
- **벨 울림 + 수락/거절** — 받는 기기에 걸려 온 통화가 뜨고, 수락해야 연결된다.
- **소켓이 없으면 FCM 푸시로 깨운다.** 세션이 살아 있는 한 목록의 모든 기기가 통화 대상이다 —
  소켓이 붙어 있으면 즉시 울리고, 아니면 알림을 보낸다([push.md](./push.md)).
- **벨은 45초다.** 서버가 재고, 지나면 양쪽을 끊는다. 늦게 알림을 연 기기는 빈 화면이 아니라
  **"이미 끝난 통화"**를 본다.
- **시그널링 게이트웨이** — `services/socket`에 **클라 → 서버 방향을 처음 연다**(§6).
  SDP offer/answer·ICE 후보를 두 세션 사이에서 **릴레이만** 한다(미디어는 안 지나간다).
- **통화 컨트롤** — 마이크 음소거 · 카메라 on/off · 종료(hang up).
- **연결 가시화** — 카드 머리의 연결 상태 배지 + 통화 아래 **접이식 진단 패널** 네 절:
  품질 지표 6개(`getStats()`) · ICE 후보 쌍과 경로 · 연결 설정(ICE 정책 2택 · 장치) ·
  시그널링 로그. **접혀 있는 것이 기본**이라 첫 인상은 제품이다(§4).

### 의도적 제외

- **링크 공유 · 방 코드 · 익명 참여** — 통화 상대가 **이미 인증된 내 세션**이라 방·TTL·정원
  강제·`room-full`이 통째로 필요 없어졌다. 보안 경계도 "이 세션 id가 내 것인가" 하나로
  좁아진다(§7). 남과 통화해야 할 이유가 생기면 그때 별도 슬라이스로 연다 — 그때 필요한 것은
  화면이 아니라 **초대받은 사람을 어떻게 인증할 것인가**이고, 그건 이 슬라이스의 질문이 아니다.
- **`POST /api/rooms`** — 함께 사라졌다. 이 슬라이스는 **새 REST 엔드포인트를 하나도 만들지
  않는다.** 필요한 조회는 이미 있는 `GET /auth/sessions`이고, 나머지는 전부 소켓이다.
- **다자(N-party)·SFU/미디어 서버** — 1:1엔 불필요하고, 미디어 서버는 슬라이스 취지
  (도메인 복잡도 X, 구현 품질 O)와 인프라 비용을 키운다.
- **녹화·저장·자막** — PII·저장 유발. 미저장 원칙과 충돌.
- **채팅/파일 전송(데이터 채널)** — v1은 미디어에 집중.
- **설정-먼저 콘솔 · 해상도/코덱 선택 · ICE 후보 필터 행렬 · 로그 레벨 필터** — 참고한 KVS
  테스트 페이지에서 버린 것들이다. 이유는 §4 대비표에 하나씩 적었다.
- **잠든 기기 깨우기** — 세션이 만료된 기기는 대상이 아니다. 세션이 없으면 토큰도 없다
  ([push.md](./push.md) §5-4). **푸시 때문에 세션 idle 수명을 늘리지 않는다** — 알림 기능이
  인증 정책을 끌고 가면 안 된다.
- **부재중 기록** — 놓친 통화 목록을 두지 않는다. 저장이 생기고, 그 저장은 세션보다 오래 산다.
  늦게 연 기기는 그 순간 한 번 "끝난 통화"를 보고 끝이다.

## 3. 사용자 흐름

### 3.1 Happy Path

1. 로그인 사용자가 `WebRTC` 진입 → **Lobby**. 오른쪽에 **내 기기 목록**
   (`GET /auth/sessions`)이 뜬다.
   > **로비는 카메라를 열지 않는다.** 진입만으로 권한을 묻지도 않는다 — 이미 허용된
   > 기기에서만 장치 **목록**을 읽고(표시등은 켜지지 않는다), 화면에는 `카메라 켜기`가
   > 선다. 실제로 여는 순간은 `Call`·`Accept`·`Test` 셋뿐이다(§4의 "명시적 제스처").
   > 세 클라이언트가 같다.
   >
   > **다만 "없다"는 미리 말한다.** 카메라도 마이크도 **하나도 없는** 기기에서는
   > 브라우저가 권한 창을 띄우지도 않고 곧바로 거절한다(`NotFoundError`) — 눌러도
   > 아무 일이 없는 화면이 되고 원인을 짐작할 단서가 없다. `enumerateDevices`는 권한
   > 없이도 장치의 **존재**를 알려 주므로(이름만 비어 있다), 그 사실은 진입 시점에
   > 그대로 옮긴다. 묻는 것이 아니라 이미 아는 것을 말하는 것이라 위 규칙과 어긋나지
   > 않고, 표시등도 켜지지 않는다. `devicechange`를 들어 두어 웹캠을 꽂으면 안내가
   > 스스로 사라진다. **웹에만 있다** — 카메라 없는 휴대폰은 사실상 없고, 네이티브는
   > 지금처럼 누른 뒤에 같은 문구로 답한다.
   >
   > 알림은 **Info**다(오류가 아니다). 타일에 얹는 이름표는 갈래마다 다르다 —
   > 하나로 뭉쳐 두었더니 영어가 `No camera access`여서, 장치가 아예 없는 기기에
   > 없는 권한 설정을 찾아가라고 말하고 있었다. **알림이 설명하고 타일은 이름표만 단다**:
   > 권한 거부 `No camera access` · 장치 없음 `No camera` · 사용 중 `Camera in use` ·
   > 비보안 `Camera unavailable`.
2. `Call` → 소켓으로 `call{to}` → 서버가 **소유권을 확인하고** `callId`를 발급하고
   **45초 타이머를 건다.** 상대에게 닿는 방법은 둘이다:
   - **소켓이 붙어 있으면** `incoming`을 바로 보낸다 → 내 화면은 **Ringing**
   - **아니면 FCM 푸시**를 보낸다(`callId` + 건 기기 종류만) → 내 화면은 **Notified**
3. 상대 기기에 **걸려 온 통화**가 뜬다(어느 화면에 있든 — 소켓은 앱 전체에 붙어 있다).
   알림으로 열었으면 앱이 소켓을 붙이고 `resume{callId}`로 아직 살아 있는지 묻는다.
   `Accept` → 서버가 타이머를 끄고 양쪽에 `accepted`.
4. **거는 쪽이 offer를 낸다** → answer → ICE 교환 → P2P 연결. 두 타일에 미디어 표시.
5. 한쪽이 종료 → `ended` → 상대는 **Lobby로 복귀**.

**45초가 지나면** 서버가 양쪽을 끊는다 — 거는 쪽은 `ended{'timeout'}`으로 로비에 돌아가고,
그 뒤에 알림을 연 기기는 `resume`에 **`expired`** 를 받아 "이미 끝난 통화"를 본다.

**루프백**은 2~4를 건너뛴다. `This tab`의 `Test`를 누르면 페이지 안에서 두
`RTCPeerConnection`이 서로에게 offer/answer를 직접 넘긴다 — 소켓도, 서버도 지나지 않는다.

### 3.2 상태 / 오류

| 상태 | 화면 |
| --- | --- |
| **권한 거부** | 프리뷰 자리에 안내 + 재요청. 기기 목록은 살려 둔다 — 오디오만으로도 통화는 성립한다 |
| **카메라 사용 중** | `NotReadableError`. 권한 거부와 **같은 타일 상태**로 접고 문구만 가른다 — 사용자가 할 일(그 앱을 닫는다)이 다르기 때문이다 |
| **걸 수 있는 기기 없음** | 목록 자리에 "탭을 하나 더 열면 자신에게 걸 수 있습니다". 막다른 화면을 만들지 않는다 |
| **호출 중(소켓)** | `Ringing` 배지 — 상대 타일이 `Waiting for an answer…` + `Cancel` |
| **호출 중(푸시)** † | `Notified` 배지 — 상대 타일이 `Waiting for the device to open…`. 왜 오래 걸리는지를 화면이 말한다 |
| **상대가 거절** | 로비로 돌아가 알림 한 줄. 오류가 아니다(Info) |
| **응답 없음** | 45초 뒤 서버가 `ended{reason:'timeout'}` → 로비 + 알림 |
| **늦게 받음** † | 창이 지난 뒤 알림을 열었다 → `resume`에 `expired` → **"이미 끝난 통화"** + 건 기기 종류. 다시 걸 수 있게 목록이 그 아래 있다 |
| **상대가 통화 중** | `callError{code:'busy'}` → 로비에 머문 채 알림. 화면 전환 없음 |
| **기기가 끊김** | 그 줄이 `Will notify`가 된다(같은 `sessionsChanged`가 목록을 새로 고친다) — 죽은 줄이 아니라 **깨우는 줄**이다 |
| **닿지 않는 기기** | 소켓도 없고 알림도 꺼져 있으면 버튼 대신 `Notifications off`. 누를 수 없는 버튼을 두지 않는다 |
| **연결 실패 / 네트워크 끊김** | `연결 실패` 배지 + 타일에 `Try again`(문구 없이). **ICE restart는 아직 없다** — 지금의 재시도는 같은 상대에게 새로 거는 것이다 |
| **상대 종료** | `ended` → **로비 복귀** + 알림. 방이 없으므로 남아서 기다릴 자리도 없다 |

> † 표시한 셋이 **켜졌다**(2026-09-05, [push.md](./push.md)). 계약에 `notified`가 들어갔고
> 서버가 소켓 없는 기기를 알림으로 깨운다 — 화면·문구·타일 상태는 이미 있던 것을 그대로 쓴다.

### 결정됨: 로비의 오른쪽 절반은 **내 기기 목록**이다

코드 입력란이 있던 자리다. 방 코드를 사람이 짓거나 받아 적는 대신, **이미 인증된 내 세션**을
고른다.

- 대시보드가 이미 그리는 목록과 **같은 데이터·같은 행 구성**이다(기기 종류 + 짧은 세션 id).
  기기명·브라우저·위치를 담지 않는 이유도 그대로 물려받는다([dashboard.md](./dashboard.md) §5).
- **소켓의 유무는 "걸 수 있는가"가 아니라 "어떻게 닿는가"를 가른다.** 세션이 살아 있으면
  전부 통화 대상이다 — `isConnected`면 즉시 울리고, 아니면 **FCM 푸시로 깨운다**.
  백그라운드로 내린 앱을 죽은 줄로 그리면 이 앱에서 가장 흔한 경우가 막힌다.
- **닿지 않는 줄만 버튼을 잃는다.** 소켓도 없고 `pushRegistered`도 false면(알림 권한 거부·
  웹 푸시 미지원) `Notifications off` 배지를 둔다. 회색 버튼을 남기면 눌러 볼 수 있는 것처럼
  보이고, 벨이 끝날 때까지 기다린 뒤에야 이유를 알게 된다.
- **내 소켓이 `ready`일 때만 `isConnected`를 믿는다.** 소켓 서비스가 죽으면 presence가 통째로
  비어 "아무도 안 붙음"과 구별되지 않는다 — 대시보드 배지가 두 갈래로 후퇴하는 것과 같은
  규칙이고, 여기서는 **모든 줄을 푸시 경로로 후퇴**시킨다. 못 거는 것보다 조금 느린 편이 낫다.
- 목록이 비면(다른 기기 없음) 빈 상태 대신 **다음에 할 일**을 적는다 — "탭을 하나 더 열면
  자신에게 걸 수 있습니다".

### 결정됨: 화면이 **어느 경로로 닿는지**를 말한다

행의 부제가 갈리고(`#7d2b90e5` ↔ `Will notify`), 호출 중 배지도 갈린다(`Ringing` ↔ `Notified`).

- 기다리는 시간이 **왜 긴지**를 화면이 설명해야 한다. 푸시 경로는 알림이 뜨고 사람이 기기를
  집어 앱을 여는 시간까지 포함하므로 소켓 경로와 체감이 다르다. 같은 `Ringing`으로 뭉뚱그리면
  느린 쪽이 고장으로 읽힌다.
- 메커니즘이 드러나는 것은 이 포트폴리오의 성격과도 맞다 — 진단 패널이 하는 일과 같은 종류다.
- **상한(45초)도 화면에 적는다**(`Calls stop ringing after 45 seconds.`). 초시계는 두지
  않는다 — 카운트다운은 화면에 시계를 하나 더 만들고, 남은 시간을 아는 것이 사용자가 할 수
  있는 일을 바꾸지 않는다. 숫자는 **이 한 줄에만** 두고 만료 화면에서 되풀이하지 않는다.
- **창은 소켓 경로에 맞춘다.** 푸시 경로를 창 안에 넣으려고 상한을 늘리지 않는다 — 늘리면
  소켓 경로의 거는 쪽이 빈 화면을 더 오래 본다. 푸시 경로의 정상 결말은 `Call expired`이고,
  그래서 배지가 `Ringing`과 `Notified`로 갈라져 있는 것이다(§8-10).

### 결정됨: 늦게 연 기기는 빈 화면 대신 **무슨 일이었는지**를 본다

창이 지난 뒤 알림을 열면 통화는 이미 서버가 끊었다. 그냥 로비를 띄우면 사용자는 알림이 잘못된
것인지, 앱이 고장인지 알 수 없다.

- `Molecule/Alert` Variant=Info로 **"이미 끝난 통화입니다 — {기기}에서 걸었습니다"**.
  오류가 아니라 사실 통지다. **초를 되풀이하지 않는다** — 상한은 호출 중 화면이 이미 말했고,
  여기서 다시 적으면 숫자가 두 곳에 살아 언젠가 어긋난다.
- **다시 걸 수 있는 목록이 바로 아래 있다.** 이것이 "부재중 목록"을 두지 않아도 되는 이유다 —
  주소록이 곧 그 화면이다.
- 부재중 **기록은 남기지 않는다**(§2). 남기려면 저장이 생기고, 그 저장은 세션보다 오래 산다.

### 결정됨: 현재 세션 줄은 지우지 않고 **루프백 시험**으로 쓴다

대시보드에서는 현재 세션 행이 `Revoke`를 갖지 않는다(자기를 끊는 버튼이라). 여기서는 반대로
**그 줄만 할 수 있는 일**이 있다.

- `Test`를 누르면 한 페이지 안에서 두 `RTCPeerConnection`이 서로 offer/answer를 넘긴다.
  **소켓도 서버도 지나지 않는다** — 그래서 진단의 시그널링 로그는 비어 있는 것이 정상이고,
  그 자리에 그렇게 적는다. `Path`도 `Loopback`으로 따로 말한다(후보 쌍이 host↔host라
  `Direct`와 구별되지 않는다).
- 값어치가 분명하다: 리뷰어가 **탭 하나로** 카메라 권한 · ICE 후보 수집 · `getStats()` 지표가
  실제로 도는 것을 확인할 수 있다. 두 번째 기기를 준비하지 못한 사람에게 이 슬라이스가
  빈 화면이 되지 않는다.
- 자기 자신을 **소켓으로** 부르는 경로는 두지 않는다. 같은 세션에 `incoming`을 보내면 벨과
  받는 화면이 한 탭에 겹치고, 서버는 자기에게 릴레이하는 특수 분기를 갖게 된다. 루프백은
  클라이언트 안에서 끝내는 것이 맞다.

### 결정됨: 받는 쪽은 **앱 어디에 있든** 걸려 온 통화를 본다

소켓은 이미 앱 전체에 붙어 있다(`SessionSocketProvider`). 그래서 걸려 온 통화는 WebRTC
페이지가 아니라 **앱 위에** 뜬다 — 대시보드를 보고 있어도 마찬가지다.

- `Organism/Modal` + `Molecule/ConfirmDialog`의 골격을 쓴다. 확인 창과 같은 무게의 결정
  (받는다/거절한다)이고, 이미 만들어 둔 모양이다.
- 거는 쪽 이름은 **기기 종류**다(`iPhone` · `Mac`). 계약에 그것밖에 없고, 그것으로 충분하다 —
  내 기기니까.
- **자동 수락은 두지 않는다.** 내 기기라도 카메라가 말없이 켜지면 안 된다. §7의
  "`getUserMedia`는 명시적 사용자 제스처 후"와 같은 줄이고, 공유되는 데모 계정에서는 더 그렇다.

### 결정됨: 프레임은 목적·구성이 바뀌거나 **화면 안에서 도달할 수 없을 때** 생긴다

다크가 프레임을 얻지 못한 이유는 "색이 변수에 묶여 있어서"가 아니라 **그림이 말하는 것이
라이트와 같아서**다([design/README.md](../design/README.md)). 연결 중·재연결·실패도 같다 —
셸·타일·컨트롤 바가 전부 같은 자리에 있고, 배지 색과 타일 안의 한 줄만 바뀐다.

그래서 **상태 시안은 프레임이 아니라 `Molecule/VideoTile`의 변형 세트에 산다.**

여기에 조건 하나를 더한다: **클릭으로 도달할 수 없는 상태는 프레임을 갖는다.** 권한 거부와
`Call expired`가 그렇다 — 앞의 것은 브라우저 설정을 되돌려야 보이고, 뒤의 것은 벨이 끝날 때까지 기다린 뒤
알림을 열어야 보인다. 구성이 로비와 같더라도, 그림이 없으면 **아무도 그 상태를 검토하지 못한다.**

| 상태 | 어디에 사는가 |
| --- | --- |
| 호출 중 · 알림 보냄 · 연결 중 · 재연결 · 실패 · 카메라 끔 · 권한 없음 | `Molecule/VideoTile`의 `State` 변형 + `Atom/Badge` 변형 |
| 상대 거절 · 응답 없음 · 상대 종료 · 상대 통화 중 | `Lobby` 구성 + `Molecule/Alert` (Info 또는 Error) |
| 늦게 받음(`expired`) | 같은 구성이지만 **도달 불가**라 프레임을 갖는다 |
| 라이트 / 다크 | 프레임의 `Colors` 적용 모드만 바꾼다 |

### 결정됨: 통화도 앱 셸 안에 있다

몰입형 전체화면 통화 화면을 만들지 않는다.

- 이 슬라이스가 증명하려는 것은 "**같은 앱**이 네 플랫폼에서 같게 동작한다"이고, 셸이 곧 그
  앱이다. 통화만 셸을 벗어나면 사이드바의 활성 항목이 사라져 지금 어디인지가 화면에서 지워진다.
- 전체화면은 **나가는 길을 하나 더** 설계해야 한다. 컨트롤 바에 이미 종료가 있는데 둘이 된다.

카드 구조는 [dashboard.md](./dashboard.md) §4 규칙 그대로다 — 카드 `padding: 0`, 좌우 여백은
각 구획이 갖고, **구분선은 각 구획의 위**에 둔다.

```text
CallCard
├── Head      20/24  제목 + 부제 | (우) 연결 상태 배지
├── Notice    ─ Molecule/Alert (거절·응답 없음·통화 중·권한, 있을 때만)
├── Stage     ─ Surface 판 + 그 위의 어두운 타일
├── Controls  ─ 14/24 · Molecule/CallControls          (데스크톱만)
└── Diagnostics ─ Organism/Diagnostics (기본 접힘)
```

> **무대 판은 `Stage`로 칠하지 않는다.** 타일이 `Stage`(어두움)이므로 판까지 같은 색이면
> 타일 경계가 사라진다. 판은 `Surface`, 타일은 `Stage` — 밝은 판 위의 어두운 타일이다.

### 결정됨: 연결 상태 배지는 카드 머리에 둔다

그것은 **통화**의 상태이지 어느 타일의 상태가 아니다. 타일 위에 얹으면 둘 중 어느 쪽 얘기인지
물어야 하고, 어두운 무대 위에 얹으려면 `Atom/Badge` 변형 전부에 어두운 표면용 짝을 만들어야
한다 — 배치 하나 때문에 변형 축이 하나 늘어난다.

| 상태 | 배지 | 키 |
| --- | --- | --- |
| 호출 중(소켓) | `Neutral` | `webrtc.status_ringing` |
| 알림 보냄(푸시) | `Neutral` | `webrtc.status_notified` |
| 연결 중 | `Info` | `webrtc.status_connecting` |
| 연결됨 | `Success` | `webrtc.status_connected` |
| 재연결 중 | `Warning` | `webrtc.status_reconnecting` |
| 연결 실패 | `Error` | `webrtc.status_failed` |

**실패 타일은 문구를 갖지 않는다** — 배지가 이미 "Connection failed"라고 말하고 있고 자세한
사정은 notice의 `Alert`가 맡는다. 타일에는 `Try again`만 둔다(대시보드의 "배지가 이미 그 말을
한다" 규칙과 같다).

> ⚠️ **`Try again`은 상대 타일에만 있다.** 그쪽은 `retryCall` — 실패한 통화를 같은 상대에게
> 새로 거는 진짜 재시도라 이름이 정확하다.
>
> **셀프 타일의 버튼은 언제나 `카메라 켜기`다.** 한때 실패 뒤에 `다시 시도`로 바꿔 달았는데,
> 그건 "되풀이하면 된다"는 약속이고 네 갈래 중 둘에서 거짓이다 — 브라우저가 기억한 권한
> 거부와 비보안 연결에서는 눌러도 같은 오류가 **즉시** 돌아온다. 이 버튼이 하는 일은 어느
> 상태에서나 "카메라를 연다" 하나뿐이라 **동작을 그대로 이름으로 쓴다.** 무엇이 잘못됐는지는
> 알림(원인과 해법)과 타일 이름표(`카메라 권한 없음`·`카메라 없음`·`카메라 사용 중`)가
> 이미 말하고 있어서, 버튼까지 실패를 인코딩할 필요가 없다.
>
> 그리고 **실패한 뒤에도 버튼은 남는다** — 오류 문구가 하나같이 "고치고 다시"라고 말하는데
> (권한 허용·다른 앱 종료·장치 연결) 버튼을 치우면 그 자리가 새로고침밖에 없는 막다른 길이
> 된다. 세 클라이언트가 같다(iOS·Android는 이 규칙이 빠져 있어 이번에 맞췄다).

### 결정됨: 피어가 왼쪽, 셀프가 오른쪽 — 그리고 셀프만 미러링한다

왼→오 읽기 순서에서 먼저 읽히는 자리가 대화 상대여야 한다. 내 얼굴은 콘텐츠가 아니라
**모니터**다. 데스크톱은 PiP가 아니라 **동등 크기** 두 타일이다 — 리뷰어가 탭 두 개로 혼자
시연할 때 두 쪽을 같이 봐야 하고, 1136 폭에서는 둘 다 충분히 크다.

상대 타일은 **절대 미러링하지 않는다**. 상대가 든 글씨가 뒤집힌다. 상대 타일의 이름표는
**기기 종류**이고 문구는 `dashboard.device_*`를 그대로 쓴다 — 같은 목록에서 온 값이라 라벨이
갈라지면 안 된다. 루프백에서는 두 타일이 같은 카메라를 나눠 쓰므로 이름표가 `Loopback`이다.

### 결정됨: 빨강은 종료에만 쓴다

음소거를 빨강으로 칠하는 관행이 있지만 그러면 화면에 빨간 원이 둘 생기고 **되돌릴 수 있는 것과
없는 것**이 같은 색이 된다. 꺼짐은 `Warning`(내가 지금 꺼 두었다는 알림), 종료는 `Destructive`.

- 컨트롤은 **48 원형**(`radius/full`), 글리프 20 — iOS 44 · Android 48을 한 값으로 만족한다.
- **종료 앞의 24px는 안전 여백이다.** 대시보드가 "모두 로그아웃"을 `Revoke` 기둥에 붙이지 않은
  것과 같은 규칙 — 되돌릴 수 없는 버튼이 반복 조작하는 버튼에 이어 붙으면 오탭이 생긴다.
- **보이는 라벨을 두지 않고 접근성 이름만 둔다.** 세 글리프는 관습이 굳었고, 라벨을 달면 바 폭이
  세 배가 되며 ko·ja에서 줄바꿈된다. 대시보드의 "터치엔 hover가 없다"에 대한 **의식적 예외**다.
- 종료 글리프의 색은 `Error Foreground`다. 하드코딩 흰색이면 다크에서 밝은 빨강(`#E08A8A`) 위에
  얹혀 대비가 나오지 않는다.
- **호출 중에는 종료를 끈다**(`Molecule/CallControls` `End=false`). 아직 통화가 아니고, 나가는
  길은 `Cancel` 하나여야 한다 — 로비 프리뷰가 같은 불리언을 쓰는 것과 같은 이유다.

### 결정됨: 좁은 폭에서 컨트롤 바는 화면 바닥에 고정한다

카드 안에 두면 진단을 폈을 때 바가 화면 밖으로 밀려 **종료 버튼에 닿을 수 없다.** 상태에 따라
자리를 옮기는 대신 **항상** 바닥에 둔다 — 조건부 이동은 두 배치를 다 유지해야 하고, 모바일 통화
앱의 관습과도 맞는다. 데스크톱은 페이지가 짧아 그 문제가 없고, 넓은 화면 바닥에 붙은 바는 카드와
따로 노는 조각이 된다.

375의 나머지 갈라짐: 두 타일을 나란히 두는 대신 **피어 전면 + 셀프 PiP(우상단)**, 컨트롤·셀렉트
높이 39 → **44**(손가락 표적), 기기 목록은 프리뷰 아래로 내려와 한 열로 쌓인다.

> **PiP는 우상단이다.** 우하단은 이름 칩·컨트롤과 겹치고 좌하단은 이름 칩 자리다. 상태 배지를
> 카드 머리에 둔 결정이 우상단을 비워 줬다. PiP에는 이름표를 달지 않고 흰 테두리만 준다 —
> 96 폭에서 칩이 판을 다 먹고, 배경 타일과 같은 `Stage` 색이라 경계가 필요하다.

### 결정됨: 진단은 덮지 않고 민다

접이식 인라인 전개다. 시트도, 모달도, 탭도 아니다.

- 진단하려는 대상이 **영상**인데 그 위를 덮으면 지표와 화면을 같이 볼 수 없다.
- 시트는 드래그 핸들·백드롭·스냅 포인트가 딸린 **플랫폼 모양의 새 컴포넌트**다 — iOS·Android에
  각각 빚이 생긴다. 접이식은 이미 세 번 만들어 본 모양이다.
- 페이지가 길어지는 것은 문제가 아니다. 사용자가 **직접 펴서** 길어진 것이다.

접혀 있어도 **요약을 보여준다**(`RTT 24 ms · ↑ 1.2 Mbps · relay`, 모바일은 두 값). 접힌 행이
아무 말도 안 하면 열어 볼 이유를 화면이 주지 못한다. 아직 연결이 없으면 옛 수치가 아니라 `—`다.

> **375에서 떨어져 나가는 것은 대역폭이지 경로가 아니다** — `24 ms · Relayed (TURN)`.
> 이 슬라이스가 답하려는 질문이 "직통인가 릴레이인가"이고, 순간 상행 대역폭은 그다음이다.
> 좁을 때는 `RTT` 접두어도 뗀다. 경로는 **번역된 이름**으로 적는다(시안의 `relay`는
> 후보 타입을 그대로 쓴 축약 표기다).
셰브런은 **펴지는 방향**을 가리킨다(`Chevron Down` ↔ `Chevron Up`).

절 순서는 **Quality · Connection · Settings · Signaling** — 읽는 순서가 곧 "지금 어떤가 → 왜
그런가 → 바꿔 본다 → 무슨 일이 있었나"다. 로그는 유일하게 계속 자라는 영역이라 맨 아래에 두고
**내부 스크롤**을 갖는다(데스크톱 220 · 모바일 160).

### 결정됨: 로그에 레벨을 두지 않고 방향을 둔다

우리 로그의 원소는 §6 계약의 메시지뿐이다. 이것을 DEBUG/INFO/WARN/ERROR 네 레벨로 나누면
**필터 UI가 원소 수보다 커진다.** 대신 **방향**(`→` 보냄 / `←` 받음)으로 가른다 — 시그널링에서
실제로 헷갈리는 축이 그것이고, §6의 "누가 offer를 내는가"가 바로 그 질문이다. 색은 오류 줄에만
쓴다. `Copy log`는 사용자가 누를 때만 동작하고 자동 전송은 없다(§7).

### 결정됨: 바꿀 수 있는 것은 두 가지뿐이다

**ICE 정책**(`STUN + TURN` / `TURN only`)과 **장치**(카메라 · 마이크). 그 밖의 KVS 설정은 전부
읽기 전용 값으로 바꿨다(아래 대비표).

`TURN only`를 남긴 이유가 중요하다 — TURN을 v1부터 넣기로 한 §8-2가 값을 하는지 **화면에서
증명하는 유일한 스위치**다. 누르면 진단의 `Path`가 즉시 `Relayed (TURN)`으로 바뀐다.

### 결정됨: 모노는 여기서 처음 쓴다

`Code`(14) · `Code/Small`(12, 신규) 두 스타일은 값·타임스탬프·후보 문자열처럼 **자리가 흔들리면
안 되는 것**에만 쓴다(1자리↔3자리 ms가 매초 바뀐다). 라벨은 Manrope 그대로다 — 모노는 **읽는
글**이 아니라 **재는 값**에 쓴다. 짧은 세션 id(`#a3f1c204`)도 여기 속하고, 대시보드가 이미
같은 모양으로 그리고 있다. 375에서는 로그의 밀리초를 뺀다(`Atom/LogLine` `Compact=Yes`).

지표는 값이 없으면 0이 아니라 `—`를 그린다. Safari는 `getStats()`의 일부 필드를 주지 않고,
없는 숫자를 0으로 그리면 화면이 거짓말을 한다.

### KVS 테스트 페이지에서 무엇을 가져오고 무엇을 버렸나

참고한 것은 [AWS KVS WebRTC 테스트 페이지](https://awslabs.github.io/amazon-kinesis-video-streams-webrtc-sdk-js/examples/index.html)다.
그 화면은 **SDK를 시험하는 하네스**이고 우리 화면은 통화를 **하는 제품**이다. 무엇을 버렸는지가
이 슬라이스의 화면 설계 그 자체다.

| KVS 요소 | 결정 | 이유 |
| --- | --- | --- |
| AWS 자격증명 입력란 | **버림** | 통화 상대가 내 세션이라 인증은 이미 끝나 있다. 입력란을 두는 순간 그 값이 어디 남는지를 우리가 책임져야 한다 |
| Signaling channel 이름 입력 | **버림 → 기기 목록** | 사람이 채널 이름을 짓는 대신 **이미 인증된 내 세션**을 고른다. 추측 가능한 이름도, 정원 강제도 필요 없어진다 |
| `Start Master` / `Start Viewer` | **버림 → `Call` 하나** | 역할이 **방향에서 나온다** — 건 쪽이 offer를 낸다. 고르게 하면 둘 다 master를 고르는 실수를 화면이 허용한다 |
| `Send Video` / `Send Audio` 체크박스 | **바꿔 채택** | 입장 전 설정이 아니라 **통화 컨트롤**(음소거·카메라)로. 체크박스는 되돌리려면 재입장해야 한다는 뜻이 된다. 로비 프리뷰에도 같은 컨트롤을 얹는다 |
| 해상도 라디오 | **버림 → 결과만 표시** | `getUserMedia`에 ideal만 주고 실제 값은 `Video` 지표로. 고르게 하면 기기가 지원하지 않는 조합에서 조용히 실패하고, 그 실패를 설명하는 화면을 또 만들어야 한다 |
| NAT traversal 라디오 4개 | **2개로 줄여 채택** | `STUN only`·`Disabled`는 **일부러 실패를 만드는** 스위치다. §2가 약속한 것은 "연결이 어떻게 되는지"이지 "어떻게 깨지는지"가 아니다 |
| Trickle ICE 체크박스 | **버림** | 계약이 `ice`를 개별 릴레이하는 구조라 trickle이 **기본이자 유일한** 동작이다 |
| ICE 후보 타입 필터 행렬 | **버림 → 읽기 전용으로 대체** | 체크박스 8개는 SDK 회귀 테스트용이다(조합 2^8, 대부분이 "연결 안 됨"). 답해야 할 질문은 "무엇을 걸러낼까"가 아니라 **"지금 어떤 후보 쌍으로 붙어 있나"** 다 |
| TCP/UDP · TURN transport 필터 | **버림 → 값으로 표시** | 전송은 후보 줄에 `udp`/`tcp`로 나온다 |
| 코덱 필터 | **버림 → 결과만 표시** | 코덱 선호를 UI에서 바꾸려면 SDP munging이 필요하고, 그것은 브라우저 간 호환 버그의 단골이다 |
| 엔드포인트 오버라이드 | **버림** | 임의 엔드포인트를 넣게 하면 Origin 허용목록과 세션 인증을 **화면이 우회시키는** 셈이다(§7) |
| Live Stats | **채택(재구성)** | 원본은 `getStats()` 덤프를 그대로 흘린다. **6지표**로 접는다 — 덤프는 "많이 보여준다"가 아니라 "읽을 수 없다"에 가깝다 |
| DQP Test Metrics | **버림** | 품질 회귀 테스트 지표다. 비교 기준이 없으면 숫자가 뜻을 갖지 못한다 |
| 로그 레벨 필터 | **버림 → 방향으로 대체** | 위 결정 참고 |
| 로그 `Clear` · `Copy` | **채택** | 리뷰어가 로그를 통째로 붙여넣어 보고할 수 있는 것은 실제로 값어치가 있다 |
| Master/Viewer 두 패널 | **버림** | 한 통화에 두 세션이라 타일 두 개가 전부다 |
| ICE 서버 목록 표시 | **부분 채택** | TURN 호스트·자격증명은 **표시하지 않는다**. 후보 **타입**만 보여주고 주소는 마스킹한다(§7) |
| 설정-먼저 화면 구조 | **버림** | 핵심이다. 우리는 통화가 먼저고, 엔지니어링 깊이는 **접힌 패널 안에서** 증명한다 |

## 5. 기술 아키텍처

```text
 세션 A (웹/iOS/Android)                      세션 B — 같은 사용자의 다른 기기
        │  ┌───── WS 시그널링(SDP·ICE) ─────┐        │
        │  ▼                                ▼        │
        │  ┌──────────────────────────────────────┐ │
        │  │  socket 서비스 (ws) — 시그널링 릴레이 │ │  ← 세션으로 인증(@app/session)
        │  │  통화 상태(callId ↔ 두 세션)만 쥔다   │ │
        │  └──────────────────────────────────────┘ │
        └──────────  P2P 미디어(직접, 서버 미경유)  ─┘
                      STUN(공개) / TURN(coturn·env)

 루프백:  한 페이지 안에서 PC1 ⇄ PC2 — 소켓도 서버도 지나지 않는다
```

- **시그널링 = socket 서비스.** 대시보드의 세션 presence를 위해 이미 만들어 둔 서비스이고,
  거기에 업그레이드 인증 · Origin 허용목록 · 연결 레지스트리 · 백오프 클라이언트가 이미 있다.
  이제 **통화 상대를 찾는 일까지 같은 레지스트리가 한다** — "세션 id → 살아 있는 소켓"이
  presence가 이미 쥐고 있던 그 지도이기 때문이다.
- **`ConnectionRegistry`가 두 번째 값을 한다.** 원래는 "누가 붙어 있나"를 세는 물건이었는데,
  통화는 거기에 "그 세션에게 이 메시지를 넘겨라"를 더한다. 다중 인스턴스로 가면
  `@app/redis` pub/sub으로 승격해야 하는 자리도 그대로 같다.
- **presence 판정은 바뀌지 않는다.** 클라 → 서버 메시지가 생겨도 **서버는 여전히 소켓의 존재만
  보고** `isConnected`를 정한다. 시그널링 메시지를 살아 있다는 증거로 쓰지 않는다 —
  `contracts.ts`가 클라 → 서버 방향을 두지 않았던 이유가 바로 그것이고(반쯤 죽은 소켓이 계속
  Active로 남는다), 그 이유는 지금도 유효하다.
- **통화 상태**는 프로세스 메모리로 시작(단일 kind 노드, `replicaCount: 1`).
  `callId → {caller, callee, phase}` 하나면 되고, 다중 인스턴스로 가면 `ConnectionRegistry`와
  **같은 자리에서 같은 승격**을 한다.
- **진단은 서버를 늘리지 않는다.** 지표는 클라이언트의 `getStats()`에서 읽고, 로그는 §6 계약
  메시지를 그대로 담은 **메모리 링 버퍼**(상한 N줄)다 — 저장하지도 전송하지도 않는다.
- **STUN/TURN**: 공개 STUN + **TURN(coturn)을 v1부터 포함**. TURN 호스트와 **공유 비밀**은
  **env로만** 주입한다(레포에 금지). ICE 서버 목록은 소켓이 `accepted`와 함께 내려준다 —
  **자격증명은 통화마다 새로 발급되고 시한부다**(coturn `use-auth-secret`, 아래 §7).
- **서버는 신규 의존성 없음**: 전송은 이미 들어와 있는 `ws`다. 웹도 브라우저 표준
  (`RTCPeerConnection`/`getUserMedia`)뿐이다. **네이티브만 런타임이 하나씩 붙었다** —
  iOS는 `stasel/WebRTC`(SPM), Android는 `io.github.webrtc-sdk:android`. 브라우저가 공짜로
  주던 것을 사 오는 것이라 피할 수 없고, 계약과 상태 기계는 그 위에서 웹과 같다.
- **nginx**: `/socket` location에 **WebSocket Upgrade**가 이미 적용돼 있다
  ([infra/deploy/README.md](../infra/deploy/README.md)). 시그널링을 같은 서비스에 두면 추가
  설정이 없다. **새 REST 엔드포인트도 없다.**

## 6. 시그널링 계약

`contracts.ts`(→ web `contracts.gen.ts`)에 **타입 + 디코더**로 둔다. 경계에서 파싱·검증
(parse, don't validate)해 형식이 어긋나면 무시/오류.

> **이 저장소에서 소켓의 클라 → 서버 방향이 처음 열린다.** 지금 `contracts.ts`는
> "클라 → 서버 메시지는 없다"고 적고 있고 그 이유는 presence였다. 그 이유는 그대로 지키고
> (§5), 방향만 시그널링을 위해 연다. 그래서 **두 계약을 이름으로 갈라 둔다** —
> `SocketServerMessage`(presence, 기존)와 `CallClientMessage`/`CallServerMessage`(통화, 신규).

```ts
// 클라 → 서버
type CallClientMessage =
  | { type: 'call'; to: string }                          // 대상 세션 id
  | { type: 'accept'; callId: string }
  | { type: 'decline'; callId: string }
  | { type: 'cancel'; callId: string }                    // 거는 쪽이 호출을 접는다
  | { type: 'offer'; callId: string; sdp: string }
  | { type: 'answer'; callId: string; sdp: string }
  | { type: 'ice'; callId: string; candidate: IceCandidate }
  | { type: 'hangup'; callId: string }
  // 알림으로 열었다 — 이 통화가 아직 살아 있나. 소켓이 붙자마자 묻는다.
  | { type: 'resume'; callId: string };

// 서버 → 클라 (기존 presence 메시지에 더해)
type CallServerMessage =
  | { type: 'incoming'; callId: string; from: SessionRef }   // 받는 쪽에 벨
  | { type: 'ringing'; callId: string }                      // 거는 쪽 — 상대에게 전달됐다
  | { type: 'accepted'; callId: string; iceServers: IceServer[] }
  | { type: 'declined'; callId: string }
  | { type: 'offer'; callId: string; sdp: string }
  | { type: 'answer'; callId: string; sdp: string }
  | { type: 'ice'; callId: string; candidate: IceCandidate }
  | { type: 'ended'; callId: string; reason: 'hangup' | 'peer-gone' | 'timeout' }
  // 알림을 늦게 열었다. 빈 화면 대신 무슨 일이었는지 그리라고 from을 함께 준다.
  // (from은 선택이다 — 아래 참조)
  | { type: 'expired'; callId: string; from?: SessionRef }
  | { type: 'callError'; code: 'unreachable' | 'busy' | 'unknown-session' | 'self' };

// 벨의 상한. 서버 상수이고 클라이언트는 재지 않는다.
const RING_TIMEOUT_MS = 45_000;

// 상대를 가리키는 값은 기기 종류뿐이다 — 화면이 필요로 하는 전부이고,
// 그 이상은 담지 않는다(dashboard.md §5의 개인정보 미저장과 같은 선).
interface SessionRef { id: string; device: DeviceKind }

// 후보는 문자열 하나가 아니다 — `addIceCandidate`는 sdpMid와 sdpMLineIndex가 둘 다
// 없으면 거부한다. 브라우저의 `RTCIceCandidateInit`을 그대로 옮겨, 클라이언트가
// `event.candidate.toJSON()`을 실어 보낼 수 있게 한다.
interface IceCandidate { candidate: string; sdpMid?: string; sdpMLineIndex?: number }

// 릴레이가 나르는 문자열의 상한. 서버는 SDP를 해석하지 않으므로 길이와 형식이
// 여기서 볼 수 있는 전부다(§7).
const MAX_SDP_LENGTH = 16_384;
const MAX_ICE_CANDIDATE_LENGTH = 1_024;
```

- **누가 첫 offer를 내는가** — `accepted`를 받은 **거는 쪽**이다. 첫 협상의 방향이 여기서
  확정되므로 glare가 없다. 방 모델에서 "기존 피어에게만 지시한다"는 규칙이 필요했던 자리가
  통째로 사라졌다.
- **재협상은 양쪽이 낸다** — ICE 정책(§4)은 각자의 화면에서 바꾸고, 그 전환이 재-offer다.
  그래서 **여기서만 glare가 남는다**: 양쪽이 동시에 누르면 서로의 offer가 서로의 연결을
  갈아 치우고 뒤이은 answer가 갈 곳을 잃는다. 역할로 가른다 — **거는 쪽이 무례하고 받는
  쪽이 정중하다**(perfect negotiation의 politeness를 이미 있는 역할에 얹은 것이다).
  무례한 쪽은 자기 offer를 지키고 상대 것을 버리며, 정중한 쪽은 자기 것을 접고 답한다.
  정중한 쪽의 정책 변경도 사라지지 않는다 — `iceTransportPolicy`는 각 연결의 지역
  설정이라, 상대 offer에 답하려고 다시 세울 때 지금 값이 그대로 들어간다.
- **`cancel`이 `ringing` 바로 뒤에 올 수 있다.** `call`을 보내고 `ringing`을 받기 전에
  사용자가 취소하거나 화면을 벗어나면, 클라이언트는 보낼 id가 없어서 **끝낼 뜻을 기억했다가**
  id를 받는 순간 보낸다. 그동안 다음 통화는 막혀 있다 — `ringing`·`callError`에 어느
  시도의 답인지가 실려 있지 않아서, 두 시도가 겹치면 앞의 답이 뒤의 통화 것으로 읽힌다.
  (계약에 요청 id를 넣는 대신 한 번에 하나만 띄우는 쪽을 골랐다 — 사람이 통화를 거는
  속도에서는 구별할 수 없는 차이다)
- **벨을 함께 받았지만 지지 않은 연결에는 `claimed`가 간다.** `accepted`는 창구 하나에만
  가고(창구가 둘이면 answer가 둘 나간다) `ended`는 통화가 끝나야 오므로, 이것이 없으면
  다른 탭·기기가 통화 내내 벨을 붙들고 있다. **끝이 아니라 "내 차례가 아니었다"라서**
  알림도 남기지 않는다 — 다른 기기에서 받은 전화가 조용히 사라지는 것과 같다.
- **소유권은 서버가 강제한다.** `call`의 `to`가 **같은 사용자의 세션이 아니면**
  `callError{'unknown-session'}`이다. 없는 세션과 남의 세션을 **구별해 주지 않는다** —
  남의 세션 id를 넣어 존재를 떠보는 경로를 열지 않기 위해서다.
- **자기 자신에게는 걸 수 없다.** `to`가 보낸 세션과 같으면 `callError{'self'}`. 루프백은
  클라이언트 안에서 끝난다(§4).
- **한 세션은 한 통화만.** 이미 통화 중인 세션을 부르면 `callError{'busy'}`. 상한은 서버가
  강제한다(클라 신뢰 X).
- **`callId`는 서버가 발급한다**(추측 불가 난수). 클라가 만든 id를 믿으면 남의 통화에
  `ice`를 흘려 넣을 수 있다. 모든 후속 메시지는 `callId`와 **보낸 세션이 그 통화의 당사자인지**
  를 함께 확인한다.
- **상대에게 닿는 방법은 서버가 고른다.** `isConnected`면 소켓으로 `incoming`, 아니면 FCM
  푸시. 클라이언트는 어느 쪽인지 **요청하지 않고** 결과(`ringing` / `notified`)를 받는다 —
  경로 선택을 클라가 쥐면 푸시를 강제로 쏘는 경로가 열린다.
- **푸시 페이로드에는 `callId`와 건 기기 종류만 담는다.** SDP·ICE·세션 id·사용자 정보는
  넣지 않는다. 알림은 잠금화면에 뜨고 OS 로그에 남는다(§7).
- **응답 없음은 서버가 끊는다** — 벨은 `RING_TIMEOUT_MS`(45초)이다. 지나면 양쪽에
  `ended{'timeout'}`을 보내고 통화를 지운다. 받는 쪽이 조용히 사라져도 거는 쪽이 영원히
  울리지 않는다. **타이머는 서버만 갖는다** — 클라가 재면 시계가 두 벌이 되고 어긋난다.
- **`resume`은 늦게 온 기기의 유일한 질문이다.** 살아 있으면 `incoming`, 아니면 `expired`.
  통화가 없어졌는지와 **애초에 남의 통화였는지**를 구별해 주지 않는다 — `unknown-session`과
  같은 이유다.
- **`expired`의 `from`은 선택이다**(2026-08-28 구현에서 갱신). 서버가 그 통화를 더는
  기억하지 못하거나(끝난 통화의 보존 창이 지났다) **애초에 내 통화가 아니었으면** 기기
  종류를 지어내지 않는다. `from`을 필수로 두면 그 두 경우에 답이 갈려, 위에서 막아 둔
  "남의 callId를 떠보는" 경로가 `resume`으로 다시 열린다. 화면은 그때 제목만 그린다 —
  `expired_title`이 기기 이름을 쓰지 않으므로 문구를 새로 만들지 않아도 된다.
- **한 세션이 탭 여럿으로 소켓을 열 수 있다** — 그래서 **소유권은 세션으로, 배달은
  연결로** 본다. 벨(`incoming`)은 그 세션의 모든 연결에 울리고, **먼저 받은 연결이
  창구**가 된다. 이후 SDP·ICE는 창구끼리만 오간다 — 세션 단위로 뿌리면 함께 벨을 받았던
  탭이 answer를 하나 더 보낸다. 종료 알림은 다시 모든 연결로 간다(끝난 통화의 모달을
  붙들고 있지 않게).
- **진단 로그의 원소는 이 계약의 메시지 그대로다.** 로그를 위한 이벤트를 새로 만들지 않는다 —
  만드는 순간 계약이 두 벌이 되고, 화면이 서버에 없는 것을 약속하게 된다.

## 7. 보안

통화는 **인증된 내 세션끼리만** 오간다. 방·링크를 버린 결정(§8-5)이 보안 경계를
"이 세션 id가 내 것인가" 하나로 좁혀 준 자리이기도 하다.

**누가 걸 수 있는가.** WS 연결은 세션으로 인증하고(`@app/session` 재사용, 비로그인 차단),
통화 대상이 **같은 사용자의 세션인지 서버가 확인한다** — 아니면 존재 여부를 구별해 주지
않고 한 코드로 거절한다(`unknown-session`). `callId`는 서버가 발급한 난수이고 모든 후속
메시지에서 당사자를 다시 확인한다. 세션당 동시 통화 1건과 벨 타임아웃은 **서버가
강제한다** — 클라이언트를 믿지 않는다.

**무엇이 서버를 지나는가.** 시그널링은 **릴레이만** 한다. 미디어는 P2P라 서버를 지나지
않고, 녹화도 저장도 없다. SDP·ICE 페이로드에는 크기 상한과 형식 검증(디코더)을 두어
릴레이를 남용·오염시킬 수 없게 했다. 시그널링 메시지는 **presence의 근거가 되지 않는다** —
`isConnected`는 여전히 소켓의 존재만 본다(§5).

**화면이 무엇을 드러내는가.** 이 포트폴리오는 스크린샷으로 돌아다니므로 진단 패널이
특히 조심스럽다.

- `getUserMedia`는 **명시적 사용자 제스처 뒤에만** 부른다. 자동 수락은 없고, 세 클라이언트
  모두 `Call`·`Accept`·`Test`에서만 연다(§3.1·§4). 공유되는 데모 계정에서는 더 중요하다 —
  아무나 내 데모 세션에 걸 수 있다는 뜻이므로 벨과 수락/거절을 반드시 지난다.
- 진단은 **SDP·ICE 본문을 표시하지 않는다.** 로그의 원소는 메시지 타입과 바이트 수뿐이고
  (`sdp 3.2 kB`), `ended`·`callError`만 사유를 덧붙인다.
- 후보 **주소는 마스킹한다**(`srflx · udp · address hidden`). 지표 수집기가 주소 필드를
  **아예 읽지 않는다**(세 플랫폼 모두). P2P라 브라우저는 어차피 상대 IP를 알지만,
  **화면에 띄우는 것은 다른 문제**다.
- **TURN 호스트·자격증명은 화면에 띄우지 않는다.** `accepted`가 실어 온 `iceServers`는
  연결에만 쓰이고 진단 어디에도 그리지 않는다. 값 자체는 **env로만** 주입한다(레포 미포함).
- **TURN 자격증명은 시한부다.** 정적 사용자명·비밀번호를 내려보내면 통화를 한 번
  성사시킨 사람이 그 값을 **영구히** 쥔다 — 세션을 폐기해도 로그아웃해도 릴레이가 열려
  있고, 화면에 안 띄운다는 것은 방어가 아니다(브라우저 콘솔에 그대로 있다). 그래서
  coturn을 `use-auth-secret`으로 세우고, 서버가 통화마다
  `username = <만료 unix>:<사용자 id>` · `credential = base64(HMAC-SHA1(공유 비밀, username))`을
  만들어 내려준다. **공유 비밀 자체는 나가지 않고**, 새어 나간 자격증명은 `PRISM_TURN_TTL`
  (기본 12시간)이 지나면 죽는다. 수명이 하루 단위인 것은 자격증명이 **통화 수락 때 한 번만**
  발급되고 그 뒤의 재협상과 릴레이 갱신이 같은 값을 다시 쓰기 때문이다 — 통화보다 짧으면
  멀쩡히 통화하던 사람의 릴레이가 도중에 끊긴다(§9). coturn의 `user-quota`가 실제로 값을 하게 되는 것은 덤이다 —
  사용자명이 하나뿐이던 시절에는 그 값이 배포 전체의 동시 할당 상한이었다.
- **시그널링에는 개수 상한이 있다.** 프레임 **크기**만 막으면(§7의 SDP 상한) 한 연결이
  같은 메시지를 무한 반복해 파드의 CPU와 Redis 왕복을 가져간다. 창(10초)마다 프레임
  120개, 그중 저장소를 건드리는 `call`·`sessionsRevoked`는 10개까지다. 넘친 프레임은
  **버리되 연결은 끊지 않는다** — 계약에 없는 메시지를 다루는 규칙과 같다.
- 진단 로그는 **메모리 링 버퍼**다(상한 200줄). 저장도 자동 전송도 없고, `Copy log`는
  사용자가 누를 때만 클립보드로 간다.

**알림 폭탄은 막았다**(2026-09-05). 프레임 상한은 여전히 **연결당**(창 10초에 `call` 10개)
이라 소켓을 여럿 연 클라이언트는 그만큼 곱해 걸 수 있는데, 소켓 경로에서는 벨이 겹칠
뿐이지만 **푸시 경로에서는 잠금화면이 배너로 덮인다.** 그래서 깨우기에는 세션당 상한을
따로 뒀다 — 창 60초에 3회, 넘으면 `unreachable`이다(사유를 나누지 않는 이유는 "너무 자주
걸었다"가 사용자가 고칠 수 있는 일이 아니어서다). `bySession`과 같은 프로세스 메모리라
다중 인스턴스로 가면 **같은 자리에서 같은 승격**을 한다.

**아직 아닌 것.** **통화 중 세션 종료**의 화면 처리가 남았다([dashboard.md](./dashboard.md)가
이 슬라이스로 넘긴 항목, §9): 서버 쪽은 끝났지만(폐기 → 소켓 종료 → `ended{'peer-gone'}`)
재로그인 뒤 보던 자리로 돌아오는 것까지가 남았다.

**푸시가 지키는 셋은 [push.md](./push.md)가 갖고, 셋 다 지켜졌다**(2026-09-05):
페이로드에 `callId`와 기기 종류만 싣기(알림은 잠금화면에 뜨고 OS 로그에 남는다 —
페이로드를 만드는 순수 함수 하나가 그 사실을 스펙으로 못박는다), FCM 등록 토큰을 응답에
싣지 않고 파생 불리언 `pushRegistered`만 노출하기, 푸시 대상을 **서버가 세션 레코드에서
꺼내기**(클라이언트는 "이 세션에 보내줘"라고만 한다 — 경로 선택을 클라가 쥐면 푸시를
강제로 쏘는 길이 열린다, §6).

## 8. 결정 (확정)

1. **미디어 콜 vs 데이터 채널** → **1:1 화상/음성 콜**로 확정(임팩트 큼).
2. **TURN** → **v1부터 TURN(coturn) 포함**(env 주입). 대칭 NAT/방화벽에서도 연결되게 한다.
3. **시그널링 전송** → **`ws`**(얕고 계약을 우리가 쥔다). socket.io 미사용.
4. **게이트웨이 위치** → **`services/socket`**. 원래 api로 잡았으나, 대시보드의 세션
   presence가 그 서비스를 먼저 만들면서 인증·Origin·레지스트리·재연결이 모두 거기에
   생겼다 — 두 번째 게이트웨이를 세울 이유가 없다(2026-08-23 갱신).
5. **상대를 어떻게 고르는가** → **내 활성 세션을 호출한다**. 일시적 방 + 링크 공유를
   버렸다(2026-08-28). 버린 쪽이 더 많은 것을 만들어야 했기 때문이다 — 방 발급 REST ·
   TTL · 정원 강제 · `room-full` · 추측 불가 id · 링크를 여는 **미인증 사용자를 어떻게
   다룰 것인가**. 반면 세션 호출은 **이미 있는 것**(세션 · presence 소켓 · 세션 목록)에
   메시지 몇 개를 얹는 일이고, 보안 경계가 "이 세션 id가 내 것인가" 하나로 좁아진다.
   남과 통화하는 것은 다른 슬라이스의 질문이다.
6. **자기 자신** → **클라이언트 루프백**. 같은 세션에 소켓으로 `incoming`을 보내면 벨과
   받는 화면이 한 탭에 겹치고 서버에 자기-릴레이 분기가 생긴다. 한 페이지 안에서 두
   `RTCPeerConnection`을 잇는 쪽이 코드도 적고, **시그널링 없이도 미디어 파이프라인이
   도는 것**을 따로 보여 주는 값어치까지 있다.
7. **수락 단계** → **벨 + 수락/거절**. 내 기기라도 카메라가 말없이 켜지면 안 된다.
   §7의 "`getUserMedia`는 명시적 제스처 후"와 같은 줄이고, 공유되는 데모 계정에서는 더 그렇다.
8. **소켓의 방향** → **클라 → 서버를 연다**(시그널링에 한해). 지금까지 단방향이었던 이유는
   presence였고 그 이유는 지금도 유효하므로, **`isConnected` 판정은 여전히 소켓의 존재만
   본다** — 시그널링 메시지를 살아 있다는 증거로 쓰지 않는다(§5).
9. **소켓 없는 기기** → **FCM 푸시로 깨운다**(2026-08-28). `isConnected`를 "걸 수 있는가"의
   기준으로 쓰면 백그라운드로 내린 앱 — 이 앱에서 가장 흔한 상태 — 이 전부 죽은 줄이 된다.
   소켓의 유무는 이제 **어떻게 닿는가**만 가르고, 못 거는 줄은 소켓도 토큰도 없는 경우뿐이다.
   대신 이 슬라이스가 [push.md](./push.md)에 의존하게 되므로 **배포를 두 단계로 나눈다**:
   소켓 경로 먼저, 푸시 깨우기는 push 슬라이스와 함께. 한 슬라이스가 다른 슬라이스를
   기다리게 두지 않으려는 것이다.
10. **벨의 상한** → **45초, 서버가 잰다**(2026-08-28 갱신, 처음엔 1분으로 잡았다).
   지나면 양쪽을 끊고, 늦게 알림을 연 기기는 `expired`로 "이미 끝난 통화"를 본다.

   **45초는 소켓 경로에 맞춘 값이다.** 상대 앱이 이미 열려 있고 수락 모달이 화면에 떠 있는
   경우이고, 리뷰어가 탭 두 개로 실제 겪는 경로이기도 하다. 소비자 통화 앱들이 대체로
   30~60초 대에 있는 것과도 어긋나지 않는다.

   **푸시 경로를 이 창에 맞추지 않는다.** 평범한 FCM 알림은 배너가 뜨고 사람이 알아차려
   앱을 여는 시간까지 포함하므로 창을 넘기기 쉽다. 그렇다고 창을 늘리면 **소켓 경로의 거는
   쪽이 빈 화면을 더 오래 본다** — 한 상수가 성격이 다른 두 시계를 겸하고 있어서 생기는
   문제이고, 어느 쪽으로 조정해도 다른 쪽이 나빠진다. 그래서 **버리는 쪽을 정한다**:
   푸시 경로의 정상 결말은 `Call expired` + 되걸기다. 화면이 이미 그렇게 돼 있어
   (`Notified` 배지가 `Ringing`과 갈라져 있고, 늦게 연 기기는 되걸 목록을 본다) 추가 비용이
   없다. **푸시는 "기기를 울린다"가 아니라 "걸었다는 사실을 알린다"** 이다.

   시계를 소켓용·푸시용 둘로 쪼개지 않는다 — 화면 문구가 조건부가 되고, 디버깅할 숫자가
   둘이 되고, 그 둘이 어긋나는 날이 온다. **부재중 기록도 남기지 않는다** — 저장이 생기고,
   그 저장은 세션보다 오래 산다.

## 9. 오픈 이슈

- **만료에도 이제 알림이 간다**(2026-09-10). 접속·해제·폐기에는 `sessionsChanged`가
  있었는데 **만료에만 없었다** — 소켓이 붙어 있는 화면도 만료된 줄을 계속 들고 있었다.
  presence 스윕이 20초마다 사용자별 목록을 읽어 지난 틱과 대조하고, 달라졌을 때만 알린다.

  **Redis keyspace notification을 쓰지 않은 이유**: pub/sub이라 파드가 재시작 중이면
  이벤트가 유실돼 어차피 안전망이 필요하다. 스윕은 놓쳐도 다음 틱에 잡으므로 그 안전망
  자체가 되고, `notify-keyspace-events`나 ACL의 `channels` 권한을 건드리지 않는다.
  대가는 지연이다 — 즉시가 아니라 **최대 20초**, presence·하트비트와 같은 시간 척도다.

  남는 것은 **소켓이 끊긴 화면**이다. 서버가 알릴 길이 없으므로 클라이언트가 다시 물어야
  한다 — 재연결하면 `ready`에서 강제 재조회가 돌고, 재연결 자체가 계속 실패하는 동안은
  여전히 얼어붙는다. 그 구간은 아직 열려 있다.
- **TURN 자격증명 재발급** — 지금은 `accepted` 한 번이 통화 내내 쓸 자격증명을 준다.
  그래서 수명을 통화보다 길게(12시간) 잡아야 하고, 새어 나간 값의 창도 그만큼이다.
  통화 중 재발급(청하는 메시지 + 새 목록을 내려주는 메시지)을 넣으면 수명을 분 단위로
  줄일 수 있다 — 양쪽이 협상을 다시 도는 값이라 푸시 슬라이스와 함께 볼 항목이다.
- **TURN 대역폭** — coturn은 떴고 대칭 NAT/방화벽도 뚫린다. 자격증명은 시한부가 되어(§7)
  회전이 일상 운영에서 빠졌고, 남은 것은 **대역폭**이다. `user-quota`/`total-quota`가
  상한이지만 그 상한에 닿았을 때 화면이 무엇을 말할지는 아직 정하지 않았다 — 지금은
  릴레이 할당이 실패하고 통화가 `연결 실패`로 접힌다.
- **통화 중 소켓 끊김** — 시그널링이 끊기면 서버가 통화를 접고, 양쪽 화면도 접는다
  (미디어 자체는 P2P라 잠깐 더 흐를 수 있지만 **양쪽이 같은 것을 보는 쪽**을 골랐다).
  회선이 잠깐 흔들린 것뿐이어도 통화가 끝나므로, 유예 창 + 인증된 재개(지금의 `resume`은
  벨 전용이다)가 다음 단계다. 푸시 슬라이스가 `resume`을 실제로 쓰기 시작하는 자리와 같다.
- ~~**푸시 권한 타이밍**~~ · ~~**웹 푸시 포함 여부**~~ — 둘 다 닫혔다(2026-09-05,
  [push.md](./push.md) §7의 닫힌 질문). 권한은 **로그인 화면에서 먼저** 받고(그래야 토큰이
  로그인 요청에 실린다), 웹 푸시는 **포함한다**. 남은 대가는 이 화면에 그대로 드러난다 —
  권한을 주지 않은 세션은 여기서 `Notifications off`이고, 권한은 켜졌는데 이 세션이 등록
  전이면 푸시 화면이 "다시 로그인하세요"로 말한다.
- **착신을 VoIP 푸시로 갈 것인가 — 지금은 가지 않는다.** 평범한 FCM 알림으로 45초 창을
  지키려면 사용자가 배너를 알아차려 앱을 여는 시간까지 그 안에 들어와야 하는데, 그건 기대하기
  어렵다. 창을 지키는 방법은 상한을 늘리는 것이 아니라 **다른 푸시를 보내는 것**이다 —
  iOS `PushKit` + `CallKit`, Android `CallStyle` 알림 + **high-priority** FCM은 사용자가
  아무것도 열지 않아도 기기를 네이티브로 울린다. 그런데:
  - iOS는 PushKit 푸시를 받으면 **반드시 CallKit에 보고해야 한다** — 하지 않으면 앱이 제재를 받는다
  - Android는 Doze에서 깨우려면 high-priority가 필요하고, 거기엔 할당량이 붙는다
  - 둘 다 도메인이 아니라 **플랫폼 통합 덩어리**다. 이 슬라이스의 취지(도메인 복잡도 X,
    구현 품질 O)에서 벗어나고, 넣는 순간 WebRTC 슬라이스가 아니라 "전화 앱 만들기"가 된다

  → **범위 밖으로 둔다.** 대신 푸시 경로의 정상 결말을 `Call expired` + 되걸기로 받아들인다
  (§8-10). **이 판단은 실기기 없이 낸 것이고 아직 그렇다** — Doze 상태와 알림 우선순위에
  따라 편차가 커서 실제로는 창 안에 들어올 수도 있다. 다만 그 경우에도 바꿀 것이 없다:
  되면 45초 안에 들어오고, 안 되면 `Call expired`가 받는다.

  구현은 **일반 알림 메시지**로 보낸다(무음 푸시가 아니다) — 앱이 꺼져 있어도 OS가 그려
  주고, iOS 무음 푸시는 저전력 모드·강제 종료에서 조용히 사라지기 때문이다. Android는
  통화 알림만 high priority로 두어 Doze에서도 지금 뜨게 했다. 채널도 통화와 데모를
  갈라 두었다 — 한 채널에 넣으면 사용자가 하나를 끌 때 둘 다 꺼진다.
- **통화 중 세션 종료** — [dashboard.md](./dashboard.md)가 명시적으로 이 슬라이스로 넘긴
  항목이다. **서버 쪽은 끝났다**: 세션이 폐기되면 presence 스윕이 그 소켓을 닫고, 그 close가
  통화 게이트웨이의 같은 문으로 들어와 상대가 `ended{'peer-gone'}`을 받는다 — 회선이 끊긴
  경우와 **결말이 같다**(아래 항목이 묻던 것이 이것이다). 남은 것은 화면이다: 통화 중에
  화면을 빼앗기는 것은 목록을 빼앗기는 것과 다르므로, 창만 다시 세우지 말고 **재로그인 뒤
  보던 자리로 돌아오는 것까지** 함께 설계한다. 시안에는 아직 없다.
- **웹의 `Info` 색이 시안과 다르다 — 이제 토큰만 바꾸면 된다.** 웹 구현이
  `--color-info`(#5B8FC7)·`--color-info-bg`(#E8F0FA)를 추가했고 **시안 `Info`와 정확히 같다.**
  그런데 `.badge--info`([apps/web/src/index.css](../apps/web/src/index.css))만 아직
  `--color-secondary-bg`/`--color-accent`(#EDF3FB / #4A78B8)를 쓴다 — `warning`·`error`는
  이미 제 토큰을 쓴다. 두 줄이면 맞는데, `.badge--info`를 **대시보드의 `Active` 배지가 함께
  쓰므로**(`statusOf`) 고치는 순간 배포된 화면의 색이 바뀐다. 남은 것은 그 시각 회귀를
  받아들일지 결정하는 일뿐이다.
- **`.session__code`만 시스템 모노에 남아 있다** — JetBrains Mono는 실렸고(`index.html`,
  400·500) `--font-mono`도 생겼다. 진단 패널은 그것을 쓰는데 대시보드의 `.session__code`만
  아직 `ui-monospace`를 하드코딩한다. 한 줄이면 모이지만 배포된 대시보드의 글자 모양이
  바뀐다 — 위의 `Info` 색과 **같은 성격의 결정**이라 함께 처리한다.
- **탭 2개 시연에서 카메라가 하나** — 두 번째 탭이 `NotReadableError`로 오디오만 붙는 경우가
  흔하다. 시안은 이상적인 두 영상으로 그리되, **오디오만인 것이 정상 경로**임을 구현에서
  안내한다. 루프백은 이 문제가 없다 — 한 스트림을 두 `RTCPeerConnection`이 나눠 쓴다.
- **기기 종류 라벨의 자리** — 통화 타일과 기기 목록이 `dashboard.device_*`를 쓴다. 두
  슬라이스가 함께 쓰게 됐으니 `common.device_*`로 올릴 만한데, 9개 키가 3플랫폼 생성 파일과
  함께 움직인다. `common.retry` 승격과 같은 종류의 일이라 **다음 i18n 정리에 묶는다.**
### 닫힌 질문

여기 있던 질문들이다. **지운 것이 아니라 답을 적어 둔다** — 무엇을 걱정했고 왜 걱정을
접었는지가 결정 자체만큼 쓸모 있다.

- ~~**모바일 권한/백그라운드**~~ — 끝났다(2026-09-04). 권한은 세 플랫폼이 같은 문
  (`Call`·`Accept`·`Test`)을 지나고, 백그라운드는 **통화를 끊고 소켓을 닫은 뒤 복귀 즉시
  다시 붙는다**. 오디오 입력 선택도 세 플랫폼이 같아졌다 — 웹은 `getUserMedia`로 스트림을
  다시 얻고, iOS는 `AVAudioSession.setPreferredInput`, Android는
  `JavaAudioDeviceModule.setPreferredInputDevice`를 쓴다.
- ~~**세션이 목록에서 사라지는 순간의 통화**~~ — 확인됐다(2026-08-28). 두 경로가 하나로
  모인다: 세션 폐기는 presence 스윕이 소켓을 닫는 것으로 끝나고, 그 `close`가 회선 끊김과
  **같은 핸들러**로 들어와 통화를 `peer-gone`으로 끝낸다. 통화 게이트웨이는 세션 폐기를
  따로 알 필요가 없다.
- ~~**iOS/Android 진단 범위**~~ — 정해졌다(2026-09-04): **전부 옮겼다.** 축소판을 권했었지만,
  로그 뷰도 라디오 그룹도 `LazyColumn`/`ScrollView` 한 겹이면 되어 예상보다 쌌고, 이 패널이
  이 슬라이스의 엔지니어링 깊이를 증명하는 자리라 플랫폼마다 다르게 두는 편이 더 비쌌다.
