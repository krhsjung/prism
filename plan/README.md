# plan

프로젝트 기획 및 설계 문서 모음 — 아키텍처 설명, ADR, API 명세, 작업 계획을 담습니다.

한 문서가 **하나의 수직 슬라이스**를 맡습니다. 화면·계약·정책이 한곳에 모여 있어야
"왜 이렇게 했는가"를 코드가 아니라 문서에서 찾을 수 있습니다.

| 문서 | 슬라이스 | 상태 | 내용 |
| --- | --- | --- | --- |
| [auth.md](auth.md) | 인증 | 구현 완료(4플랫폼) | 소셜 로그인 · 데모 로그인 · API 계약 · **세션 정책**(§6) · 보안 체크리스트 |
| [dashboard.md](dashboard.md) | 대시보드 | 구현(web · iOS · Android) | 로그인 이후 화면 · 활성 세션 관리 · 앱 셸 |
| [webrtc.md](webrtc.md) | WebRTC | 4플랫폼 구현 · 미배포 | **내 세션끼리** 1:1 P2P 통화 · 루프백 · 시그널링 · TURN · 통화 진단 |
| [push.md](push.md) | 푸시 | 뼈대 | FCM 푸시 · 토큰을 세션에 담는 정책 · 대상은 세션 목록 |

## 읽는 순서

1. [auth.md](auth.md) — 프로젝트의 뼈대입니다. §5 API 계약과 §6 세션 정책은
   서버·웹·iOS·Android 네 구현이 모두 참조하는 원천입니다.
2. [dashboard.md](dashboard.md) — 인증 이후의 화면. §1 기능 로그가 "무엇이 언제 왜
   추가됐는지"의 시간순 요약입니다.
3. [webrtc.md](webrtc.md) — 지금 슬라이스. §4가 화면 명세이고, §6이 시그널링 계약입니다.
   §9-5가 이 슬라이스에서 가장 큰 결정입니다 — 방·링크를 버리고 **세션 호출**로 간 이유.
4. [push.md](push.md) — 그다음 후보의 뼈대. 정해진 것은 §5 결정뿐입니다.

## 규칙

- **작업 기록은 여기 두지 않습니다** — 점검·대조처럼 만드는 과정에서만 쓰는 문서는
  저장소에 남기지 않고(`working/`, gitignore), **결론만** 해당 슬라이스 문서로 옮겨
  적습니다. 기획 문서가 저장소 밖 파일을 링크로 가리키지 않게 하려는 것입니다.

- **기능 로그** — `dashboard.md` · `webrtc.md`는 §1에 기능 로그를 둡니다. 사용자가
  체감하는 기능이 붙을 때마다 한 항목씩 최신순으로 쌓고, 상세 설계 변화는 해당
  섹션에 반영합니다(내부 리팩터는 로그가 아니라 커밋으로 충분합니다).
- **결정은 이유와 함께** — 무엇을 골랐는지보다 무엇을 버렸고 왜인지를 남깁니다.
  오픈 이슈는 문서 끝(§9 등)에 모아 둡니다.
- **화면은 Figma가 원천** — 문서에는 노드 링크를 두고 그림을 복제하지 않습니다
  ([design/README.md](../design/README.md)).
